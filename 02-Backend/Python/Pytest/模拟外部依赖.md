# 模拟外部依赖

## 📌 一句话总结
> 模拟外部依赖是单元测试的基石。它的核心目标是确保**你的业务逻辑在隔离环境下正确运行**，而不因网络超时、数据库宕机或文件权限问题导致测试失败。在PyTest生态中，我们有三层武器库：**内置`monkeypatch`**、**`pytest-mock`插件**以及**专用的文件系统模拟库`pyfakefs`**。

我将按照依赖类型（网络、数据库、文件系统）分别给出模拟策略，并对比不同方法的适用场景。

## 🎯 核心概念

### 1. 模拟网络请求（HTTP API）

最常见的场景是调用第三方REST API。目标是**不发出真实请求**，直接返回预设响应。

#### 方法一：使用 `pytest-mock`（推荐）

```python
import requests
import pytest

# 被测函数：调用外部API获取天气
def get_weather(city):
    resp = requests.get(f"https://api.weather.com/{city}")
    return resp.json()["temp"]

def test_get_weather(mocker):
    # 1. Patch 'requests.get' 在调用处
    mock_get = mocker.patch("my_module.requests.get")
    
    # 2. 构造模拟响应
    mock_response = mocker.Mock()
    mock_response.json.return_value = {"temp": 25}
    mock_get.return_value = mock_response
    
    # 3. 执行并断言
    temp = get_weather("London")
    assert temp == 25
    mock_get.assert_called_once_with("https://api.weather.com/London")
```

#### 方法二：使用 `monkeypatch`（更轻量）

如果只需要替换一个函数，`monkeypatch` 也足够。

```python
def test_get_weather_monkey(monkeypatch):
    def fake_get(*args, **kwargs):
        class MockResp:
            def json(self):
                return {"temp": 25}
        return MockResp()
    
    monkeypatch.setattr("my_module.requests.get", fake_get)
    assert get_weather("Paris") == 25
```

**进阶：模拟异常情况**

```python
def test_get_weather_network_error(mocker):
    mocker.patch("my_module.requests.get", side_effect=ConnectionError("timeout"))
    with pytest.raises(ConnectionError):
        get_weather("Berlin")
```

### 2. 模拟数据库依赖

数据库依赖通常分为两层：**DAO（数据访问对象）层**和**上层业务逻辑**。我们有两种主流策略：

#### 策略一：模拟DAO层接口（推荐，纯单元测试）

直接模拟数据库访问对象，让业务逻辑不依赖真实数据库。

```python
# dao.py
class UserDAO:
    def find_by_id(self, uid):
        # 真实SQL查询
        pass

# service.py
def get_user_name(uid, user_dao):
    user = user_dao.find_by_id(uid)
    return user.name if user else None

# test_service.py
def test_get_user_name(mocker):
    mock_dao = mocker.Mock(spec=UserDAO)
    mock_user = mocker.Mock()
    mock_user.name = "Alice"
    mock_dao.find_by_id.return_value = mock_user
    
    result = get_user_name(1, mock_dao)
    assert result == "Alice"
    mock_dao.find_by_id.assert_called_once_with(1)
```

#### 策略二：使用内存数据库（如SQLite）进行集成测试

如果逻辑包含复杂SQL（如多表联查），模拟DAO层可能工作量过大。此时可切换到真实数据库（但为内存模式）。

```python
import sqlite3
import pytest

@pytest.fixture
def db_conn():
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE users (id INT, name TEXT)")
    conn.execute("INSERT INTO users VALUES (1, 'Alice')")
    yield conn
    conn.close()

def test_find_user(db_conn):
    # 使用真实SQLite，但数据仅在内存中，速度快且隔离
    cursor = db_conn.execute("SELECT name FROM users WHERE id=1")
    assert cursor.fetchone()[0] == "Alice"
```

**注意**：如果生产使用PostgreSQL，内存SQLite可能无法完全模拟某些数据库特性（如JSON字段、存储过程）。此时可以考虑 **testcontainers** 启动真实数据库容器。

### 3. 模拟文件系统操作

文件操作分为**文件读写**和**路径/目录检查**。我们有三种方案：

#### 方案一：`tmp_path` + `monkeypatch.chdir`（避免污染项目目录）

```python
def test_write_report(tmp_path, monkeypatch):
    # 将当前工作目录切换到临时目录
    monkeypatch.chdir(tmp_path)
    
    # 被测函数内部会写 report.txt 到当前目录
    generate_report()  # 假设它在当前目录创建 report.txt
    
    # 验证
    assert (tmp_path / "report.txt").exists()
    assert (tmp_path / "report.txt").read_text() == "some content"
```

#### 方案二：`monkeypatch` 替换 `os.path` 方法（避免真实文件操作）

```python
def test_config_loader(monkeypatch):
    # 让 os.path.exists 永远返回 True
    monkeypatch.setattr(os.path, "exists", lambda p: True)
    
    # 模拟 open 读取内容
    def fake_open(*args, **kwargs):
        class MockFile:
            def read(self):
                return '{"key": "value"}'
            def __enter__(self):
                return self
            def __exit__(self, *args):
                pass
        return MockFile()
    monkeypatch.setattr("builtins.open", fake_open)
    
    config = load_config()  # 内部会读文件
    assert config["key"] == "value"
```

#### 方案三：使用 `pyfakefs`（重度文件操作测试的最佳选择）

`pyfakefs` 是一个**伪造整个文件系统**的第三方库，让所有文件操作（`os`、`pathlib`、`open`）都在虚拟文件系统上执行，无需 `monkeypatch` 逐个方法替换。

```python
# 安装: pip install pyfakefs
from pyfakefs.fake_filesystem_unittest import TestCase

def test_file_operations(fs):
    # fs 是 pyfakefs 提供的 fixture（需在 conftest.py 中注册）
    fs.create_file("/data/config.json", contents='{"env":"test"}')
    
    result = load_config_from_path("/data/config.json")
    assert result["env"] == "test"
    
    # 断言文件是否存在
    assert fs.exists("/data/config.json")
```

### 4. 对比总结：何时用哪种工具？

| 依赖类型 | 轻量方案（快速、简单） | 重量方案（真实环境模拟） |
| :--- | :--- | :--- |
| **网络请求** | `mocker.patch("module.requests.get")` | `responses` 或 `httmock` 库（可注册多个URL模式） |
| **数据库** | Mock DAO 接口（使用 `mocker.Mock`） | `sqlite3 :memory:` 或 `testcontainers` 启动真实容器 |
| **文件系统** | `tmp_path` + `monkeypatch.chdir` | `pyfakefs`（伪造完整文件系统，无需实际IO） |

### 5. 常见陷阱与最佳实践

1. **补丁位置错误**：必须 patch **被测模块中引用**的位置，而非定义处。例如，被测模块 `myapp.service` 中 `import requests`，则应 patch `myapp.service.requests.get`，而非 `requests.get`。
2. **过度模拟**：只模拟**外部边界**（网络、数据库、文件），内部函数或工具类应尽量保留真实逻辑，以免测试变成“模拟测试”而非“业务测试”。
3. **异常场景覆盖**：除正常响应外，务必模拟超时、HTTP 5xx、空数据等异常，确保代码有鲁棒的容错逻辑。
4. **确保清理**：无论用哪种工具，测试结束后依赖状态必须恢复。`mocker` 和 `monkeypatch` 自动清理，`pyfakefs` 会在 fixture 结束时重置虚拟文件系统。
5. **集成测试与单元测试分离**：使用标记（如 `@pytest.mark.integration`）区分单元测试（模拟所有外部依赖）和集成测试（使用真实依赖），在CI中分别执行。
