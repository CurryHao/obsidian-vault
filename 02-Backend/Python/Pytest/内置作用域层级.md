# 内置作用域层级

## 📌 一句话总结
> 这是PyTest固件（Fixture）设计中**最关键的资源生命周期决策**。正确选择作用域，能让你的测试套件在**速度**与**隔离性**之间取得完美平衡；选错了，则会导致测试污染或执行效率暴跌。

我将按照**生命周期时长**（从短到长）为你拆解这四个层级，并揭示其背后精密的**嵌套执行顺序**。

## 🎯 核心概念

### 1. 作用域层级速查表

| 作用域 | 实例化次数 | 生命周期起始 | 生命周期结束 | 典型应用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **`function`**（默认） | **每个测试函数** 1次 | 测试函数执行前 | 测试函数执行后立即销毁 | 轻量级对象、可变数据构造、数据库事务（每个用例独立回滚） |
| **`class`** | **每个测试类** 1次 | 类中第一个测试方法前 | 类中最后一个测试方法后 | 类级别的Mock配置、类共享的测试数据夹具 |
| **`module`** | **每个测试模块（.py文件）** 1次 | 模块中第一个测试前 | 模块中最后一个测试后 | 模块级数据库连接池、加载大型配置文件 |
| **`session`** | **整个测试会话** 1次 | `pytest` 启动时 | `pytest` 退出时（所有测试结束） | 全局应用启动、外部容器（Docker/Database）生命周期、昂贵的API客户端 |

### 2. 深入解读：每种作用域的战场

#### `function`（默认，最安全）
- **执行逻辑**：每个`test_*`函数都会触发该固件的Setup和Teardown。
- **代码示例**：
```python
@pytest.fixture
def clean_counter():
    counter = {"count": 0}
    yield counter
    # 无需额外清理，但每个测试都会拿到新的 {count:0}
```
- **选择理由**：当你需要**绝对隔离**，避免任何可变状态跨测试泄漏时。

#### `class`（逻辑分组共享）
- **执行逻辑**：类中第一个方法前执行Setup，最后一个方法后执行Teardown。若类中存在参数化方法，依然只在类整体生命周期内执行一次。
- **代码示例**：
```python
@pytest.fixture(scope="class")
def class_db_connection():
    conn = create_db_conn()
    conn.execute("CREATE TABLE temp ...")  # 一次性建表
    yield conn
    conn.execute("DROP TABLE temp ...")    # 类结束后清理

class TestUserDB:
    def test_insert(self, class_db_connection):
        # 可以共用同一个连接
        assert class_db_connection.insert(...) 
```
- **适用陷阱**：类内多个测试方法会共享状态（如`conn`事务），若某个方法修改了数据，后续方法会看到修改，需谨慎。

#### `module`（文件级缓存）
- **执行逻辑**：该固件会在模块（.py文件）中的**第一个测试执行前**完成Setup，直到该模块中**最后一个测试执行完**才Teardown。
- **典型场景**：加载一个几百MB的词库文件或AI模型。如果每个`function`都加载一次，测试会慢到无法接受；module级加载一次，整个文件内的测试都可复用。
- **注意**：如果模块内有多个测试函数修改了该对象的内部状态，顺序依赖风险上升。

#### `session`（全局单例，最高效也最危险）
- **执行逻辑**：整个`pytest`进程生命周期内只执行一次。当执行`pytest tests/`扫描所有子目录时，session级固件会在最开始被激活。
- **典型场景**：启动Docker测试容器、初始化整个测试数据库Schema、创建全局HTTP会话池。
```python
@pytest.fixture(scope="session")
def global_docker_env():
    docker_client = start_docker_compose()  # 启动所有依赖
    wait_for_healthy()
    yield docker_client
    docker_client.down()  # 全部测试结束后销毁
```
- **致命红线**：session级固件中**绝对不要**包含可变状态（如全局列表、累加器），因为所有测试共享此对象，会引发难复现的失败。

### 3. 嵌套执行顺序的“栈”机制（极其重要）

当不同作用域的`autouse`固件混合时，执行顺序遵循**Setup顺序由外到内（大->小），Teardown顺序由内到外（小->大）**，类似一个“洋葱模型”。

**执行顺序图解（以 session -> module -> function 为例）：**
```text
[Session Setup] 开始
   → [Module Setup] 开始
        → [Function Setup] 开始
             → [测试函数执行]
        → [Function Teardown] 结束
   → [Module Teardown] 结束
[Session Teardown] 结束
```

**具体代码验证（在conftest.py中）：**
```python
@pytest.fixture(scope="session", autouse=True)
def s():
    print("\nSession Start")
    yield
    print("Session End")

@pytest.fixture(scope="module", autouse=True)
def m():
    print("  Module Start")
    yield
    print("  Module End")

@pytest.fixture(autouse=True)
def f():
    print("    Func Start")
    yield
    print("    Func End")

# 执行任意测试，控制台输出会严格按上述缩进层级打印。
```
> **记忆口诀**：大先setup，小先teardown；后进先出（LIFO）。

### 4. 决策矩阵：我该选哪个？

| 考量维度 | `function` | `class` | `module` | `session` |
| :--- | :--- | :--- | :--- | :--- |
| **执行速度** | 慢（重复setup/teardown开销大） | 中 | 快 | **极快** |
| **隔离性** | **极好**（完全独立） | 中（类内共享） | 差（模块内共享） | **极差**（全局共享） |
| **调试难度** | 低（失败容易复现） | 中 | 高（污染源难定位） | **极高**（极易踩坑） |
| **推荐默认值** | ✅ **90%场景首选** | 仅当类中方法需共享昂贵的连接时 | 加载静态配置/只读数据 | 仅用于启动/停止外部基础设施 |

### 5. 极易踩中的 3 个致命陷阱

| 陷阱现象 | 根本原因 | 解决方案 |
| :--- | :--- | :--- |
| **参数化 + session固件乱序** | 将`@pytest.mark.parametrize`与`session`级固件混用，参数化产生的多个测试会重复使用同一个全局对象，导致“先跑的参数污染后续参数” | 参数化场景下，**禁用 `session`**，必须降级为 `function` 确保每组参数独立 |
| **Module级固件修改内部列表** | `my_list.append(x)` 导致模块内测试B看到了测试A添加的数据 | 若必须共享，请在固件中**返回深拷贝**（`return data.copy()`）或将可变操作封装为不可变函数 |
| **Session级清理因异常未执行** | `yield` 后的Teardown代码若前面有异常抛出，依然会执行（这是`yield`的优势）。但若**进程被强制终止（SIGKILL）**，则清理无法执行 | 编写防御性代码：在`yield`外加 `try...finally` 包裹，或依赖外部编排工具确保资源回收 |

### 6. 终极建议：保持“作用域下沉”

1. **默认无脑选 `function`**：这是`pytest`官方推荐的默认值，能保证测试独立、可预测。
2. **只有当性能测试（Profile）明确显示 `function` 作用域导致整体耗时超过5秒时**，才考虑向上提升至`module`或`session`。
3. **`session` 仅限 `conftest.py` 根目录使用**，且必须确保其返回值是**不可变的单例**（如只读的配置字典），绝不用作状态容器。

您现在是想**优化一个运行缓慢的测试套件**，通过调整作用域来提速，还是**遇到了因共享状态导致测试偶发失败**（Flaky Tests）的问题？告诉我具体痛点，我可以帮您诊断现有固件的作用域是否合理，并给出精准的重构方案。
