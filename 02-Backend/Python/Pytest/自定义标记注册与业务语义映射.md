# 自定义标记注册与业务语义映射

## 📌 一句话总结
> 这是PyTest从“测试执行工具”进化为“**企业级质量门禁系统**”的核心环节。自定义标记的本质是将**技术测试用例**映射为**业务风险维度**，让非技术人员（PM、运维）也能通过标记读懂测试策略。

我将从**注册机制**、**三大核心语义定义**、**CI流水线映射**到**企业级标记体系设计**，带你构建一套清晰、可扩展的标记规范。

## 🎯 核心概念

### 1. 注册机制：告别 `PytestUnknownMarkWarning`

在`pyproject.toml`（或`pytest.ini`）中显式注册标记，配合`--strict-markers`强制生效，杜绝拼写错误。

```toml
# pyproject.toml
[tool.pytest.ini_options]
addopts = ["--strict-markers"]  # 强烈建议开启：未注册标记直接报错，而非警告
markers = [
    # ===== 执行策略维度 =====
    "smoke: 冒烟测试（核心业务流程，PR合并前必须全绿）",
    "slow: 耗时测试（>5秒，默认不运行，仅夜间或手动触发）",
    "integration: 集成测试（依赖外部服务/数据库/网络，本地默认跳过）",
    
    # ===== 测试层级维度（可选扩展） =====
    "unit: 单元测试（纯内存逻辑，无外部依赖）",
    "e2e: 端到端测试（完整用户旅程，通常带UI或全链路）",
    
    # ===== 业务模块维度 =====
    "payment: 支付模块相关测试",
    "user: 用户认证与权限测试",
]
```

**验证注册是否生效**：
```bash
pytest --markers   # 列出所有已注册的标记及说明
```

### 2. 三大核心标记的业务语义与执行策略

| 标记 | 业务语义（给PM/运维看） | 技术特征（给开发看） | 推荐执行策略 |
| :--- | :--- | :--- | :--- |
| **`smoke`** | **“系统是否还活着？”** <br> 核心增删改查、登录、支付主流程 | 用例数极少（<20个），执行极快（<2分钟） | **每次PR合并前必须全绿**；`pytest -m smoke` 在CI的快速反馈阶段执行 |
| **`slow`** | **“哪些地方拖慢了交付？”** <br> 复杂报表计算、大数据量迁移、AI推理 | 单个用例耗时 >5秒，内存/CPU消耗大 | **默认排除**（`-m "not slow"`）；仅在夜间回归或手动 `-m slow` 时触发；需搭配 `-n auto` 并行执行 |
| **`integration`** | **“依赖的外部系统是否正常？”** <br> 数据库、Redis、第三方API、消息队列 | 需要`docker-compose`或真实测试环境，可能产生副作用 | **本地开发默认跳过**（`-m "not integration"`）；在CI的集成测试阶段（Staging环境）执行 |

### 3. 实战：标记的组合与命令行筛选逻辑

标记的强大之处在于**逻辑运算**（`and` / `or` / `not`），实现不同场景的精准筛选。

#### 场景一：本地开发（极速反馈，仅跑纯内存逻辑）
```bash
pytest -m "unit and not slow and not integration"
```

#### 场景二：PR 合并前门禁（冒烟 + 核心单元测试，必须快）
```bash
pytest -m "smoke or (unit and not slow)"
```

#### 场景三：夜间全量回归（包含慢速和集成，允许超时）
```bash
pytest -m "integration or slow or e2e" -n auto --timeout=300
```

#### 场景四：仅测试支付模块的冒烟用例（双重筛选）
```bash
pytest -m "smoke and payment"
```

### 4. 代码级应用：堆叠与继承

一个测试可以同时挂载多个标记（交并集关系），实现多维度分类。

```python
import pytest

# ✅ 标准用法：分层 + 模块
@pytest.mark.smoke
@pytest.mark.integration
@pytest.mark.payment
def test_payment_with_credit_card():
    # 该用例同时属于：冒烟、集成、支付模块
    # 执行 pytest -m "smoke and payment" 会命中它
    pass

# ✅ 标记整个类（类内所有方法继承）
@pytest.mark.slow
@pytest.mark.integration
class TestDatabaseMigration:
    def test_migrate_v1_to_v2(self): pass
    def test_rollback_v2_to_v1(self): pass
```

### 5. 企业级标记体系设计（三层架构）

良好的标记设计应像**图书馆索引系统**，而非杂乱的标签云。我推荐以下三层结构：

| 层级 | 标记前缀示例 | 用途 | 负责人关注点 |
| :--- | :--- | :--- | :--- |
| **执行层（L1）** | `smoke` / `slow` / `integration` / `flaky` | 控制“是否运行”和“何时运行” | **DevOps / CI维护者** |
| **模块层（L2）** | `auth` / `order` / `inventory` / `report` | 控制“测了哪个业务域” | **技术负责人 / QA** |
| **质量层（L3）** | `critical` / `regression` / `new_feature` | 标识“测试的重要性和变更属性” | **产品经理 / 发布经理** |

**实战示例**：一个新增的“会员等级升级”功能，标记为：
```python
@pytest.mark.smoke       # L1：冒烟，必跑
@pytest.mark.user        # L2：用户模块
@pytest.mark.new_feature # L3：新功能，需要重点观察
def test_upgrade_to_vip(): ...
```

### 6. 极易踩中的 3 个致命陷阱

| 陷阱现象 | 根本原因 | 解决方案 |
| :--- | :--- | :--- |
| **`-m "not slow"` 意外排除了同时带有 `integration` 的用例** | `not slow` 会排除所有含 `slow` 标记的用例，即使它同时有 `integration` | 使用 `and` / `or` 明确组合：`-m "integration and not slow"` |
| **标记仅在测试函数上生效，不作用于 `conftest.py` 中的 Fixture** | Fixture 本身不能挂载 `marker`，但可以通过 `request.node.get_closest_marker()` 在 Fixture 内部感知上下文 | 若必须在Fixture中根据标记改变行为，在Fixt内检测当前测试节点：`if request.node.get_closest_marker("slow"): set_timeout(60)` |
| **标记注册了，但在 `conftest.py` 中拼写错误导致静默失效** | `conftest.py` 顶部写了 `pytest.mark.smke`（拼错） | **强制开启 `--strict-markers`**，此时任何未注册的标记（包括拼写错误）会直接抛出 `UsageError`，CI立即失败，不会放过 |

### 7. 高级技巧：用标记驱动 Fixture 行为

根据测试标记动态调整 Fixture 的超时时间或配置：

```python
# conftest.py
@pytest.fixture
def api_client(request):
    client = APIClient()
    # 如果当前测试是 slow 标记，延长超时时间
    if request.node.get_closest_marker("slow"):
        client.timeout = 30
    else:
        client.timeout = 5
    return client
```

### 8. 诊断指令速查

```bash
# 查看所有已注册的标记及说明
pytest --markers

# 查看哪些测试会被某个标记表达式选中（不执行）
pytest --collect-only -m "smoke and not slow"

# 在 CI 中统计各标记的用例数量（用于门禁配额评估）
pytest --collect-only -q | grep -E "smoke|slow|integration" | sort | uniq -c
```

您现在是要为**现有项目建立从零开始的标记体系**，还是想**优化现有的混乱标记**（比如有几十个未注册的随意标记）？告诉我您项目的业务模块数量（如订单/用户/库存）和CI阶段（本地开发/PR检查/夜间回归），我可以为您生成一份**可直接贴入 `pyproject.toml` 的完整标记注册表**，并附上 `conftest.py` 中用于读取标记来调整Fixtrue的代码段。您选哪个场景？
