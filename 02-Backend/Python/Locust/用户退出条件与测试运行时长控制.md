# 用户退出条件与测试运行时长控制

在 Locust 中，**“用户退出”** 和 **“测试运行结束”** 是两个完全不同的层面。前者属于**用户生命周期管理**（微观，单个协程的行为），后者属于**全局任务调度**（宏观，整个压测进程的生命周期）。

理解二者的区别与联动机制，能帮你精准控制压测行为，避免“用户死循环”或“测试无法优雅终止”等问题。

---

### 1. 用户退出条件（微观层面：单个 Greenlet 的销毁）

单个 `User` 实例（协程）何时退出？主要有以下 **4 种途径**：

#### A. 主动抛出 `StopUser` 异常（最常用）
在 `on_start` 或 `@task` 方法中，通过 `raise StopUser()` 主动终止当前用户。这通常用于**业务逻辑无法继续**的场景（如账号余额不足、库存售罄）。

```python
from locust import HttpUser, task
from locust.exception import StopUser

class ShopUser(HttpUser):
    def on_start(self):
        resp = self.client.post("/login", json={"user": "test"})
        if resp.status_code != 200:
            # 登录失败，此用户无存在意义，直接退出
            raise StopUser()

    @task
    def buy(self):
        with self.client.post("/order", json={"sku": "X"}, catch_response=True) as resp:
            if resp.json().get("stock") == 0:
                # 库存为0，当前用户任务完成，退出
                resp.failure("库存不足")
                raise StopUser()
```
#### B. 通过 `InterruptTaskSet` 退出嵌套任务集
当在 `SequentialTaskSet` 中完成一个完整业务流程（如下单成功）后，使用 `self.interrupt()` 退出当前任务集，**若该任务集是 User 的顶级任务，则等同于退出整个用户**。

```python
from locust import SequentialTaskSet, task

class OrderFlow(SequentialTaskSet):
    @task
    def step1(self): self.client.post("/cart")
    
    @task
    def step2(self): 
        self.client.post("/pay")
        # 支付完成，退出此任务集，若没有父级TaskSet则用户停止
        self.interrupt() 
```

#### C. 隐含退出：`@task` 循环结束
理论上，只要测试未停止，`@task` 会无限循环。但若你**没有定义任何 `@task`**，用户会在执行完 `on_start` 后直接退出。

#### D. 父级强制杀死
当 Master 下发停止指令（测试时间到），或 Web UI 点击 `Stop`，所有运行中的 Worker 会**强制杀死**所有协程，此时会尽量调用 `on_stop`，但不保证一定会执行完整。

### 2. 测试运行时长控制（宏观层面：整个压测进程）

全局测试何时结束？主要由以下机制决定：

#### A. 命令行固定时长（最常用）
使用 `-t` 或 `--run-time` 参数指定运行时间，格式支持 `10s`、`5m`、`2h` 等。

```bash
# 运行 30 分钟后自动停止，并优雅等待 60 秒让 on_stop 执行完
locust -f demo.py --headless -u 100 -r 10 -t 30m --stop-timeout 60
```

-   **机制**：主计时器到期后，Master 向所有 Worker 下发 `stop` 消息。
-   **关键参数**：`--stop-timeout` 指定在强制杀死用户前，等待当前请求和 `on_stop` 执行的最大秒数，**强烈建议设置**（默认 0 秒可能导致日志/统计丢失）。

#### B. 通过 `LoadTestShape` 返回 `None`
自定义负载形状类（`LoadTestShape`）的 `tick()` 方法若返回 `None`，测试将立即终止。

```python
class MyShape(LoadTestShape):
    def tick(self):
        if self.get_run_time() > 120:  # 运行超过120秒
            return None  # 停止测试
        return (100, 10)
```

#### C. Web UI 手动停止
在 Web 界面点击 `Stop` 按钮，效果等同于发送 `--run-time` 到期信号。

#### D. 事件监听触发的程序化停止
在 `@events.test_start` 或 `@events.init` 监听器中，通过环境对象手动停止：

```python
@events.init.add_listener
def _(environment, **kwargs):
    # 如果检测到环境不合法，直接停止
    if not check_license():
        environment.runner.quit()  # 立即退出
```

### 3. 关键交互：用户退出与测试结束的时序

当你设置了 `-t 10m`，在 10 分钟到期的那一刻，Locust 会按以下顺序执行：

1.  **全局终止信号**：Master 广播 `STOP` 命令给所有 Worker。
2.  **停止孵化新用户**：Worker 立即停止孵化新的 Greenlet（即使 `spawn-rate` 尚未达到目标 `users`）。
3.  **尝试优雅退出**（重要）：
    -   所有正在执行 `@task` 或 `on_start` 的协程，会**继续执行直到当前函数结束**（不会在请求中途强行中断）。
    -   当前函数结束后，Locust 会尝试调用该用户的 `on_stop()`。
    -   如果设置了 `--stop-timeout`，系统会等待 `on_stop` 执行完毕；超时则强制回收。
4.  **聚合统计**：Worker 将最后一批统计数据上报给 Master，Master 生成 CSV/HTML 报告。

### 4. 组合策略实践：精准控制“业务退出”与“全局时长”

#### 场景 A：模拟“只完成 N 笔订单”后退出用户
结合 `StopUser` 与任务计数器，实现单用户限制。

```python
class OrderUser(HttpUser):
    order_count = 0
    max_orders = 10

    @task
    def create_order(self):
        self.client.post("/order")
        self.order_count += 1
        if self.order_count >= self.max_orders:
            print(f"User {self.user_id} 完成 {self.max_orders} 笔订单，退出")
            raise StopUser()
```

#### 场景 B：混合运行（固定时长 + 用户动态进出）
即使设置了 `-t 30m`，在 30 分钟内，单个用户可能因为业务条件（如库存售罄）而提前退出。此时，Worker 会自动孵化**新用户**来补足目标并发数（`-u`），直到测试时间结束。

```python
# 命令行
locust -f demo.py --headless -u 100 -r 10 -t 30m

# 行为：若 100 个用户中有 30 个因无库存退出了，Worker 会再孵化 30 个新用户，保持总数为 100，直至 30 分钟截止。
```

#### 场景 C：精确到“秒”的波动结束
如果你想在压测最后阶段模拟“流量退潮”，使用 `LoadTestShape` 返回 `(0,0)` 或 `None` 实现锥形收尾。

```python
class TaperShape(LoadTestShape):
    def tick(self):
        run_time = self.get_run_time()
        if run_time < 60:
            return (100, 10)
        elif run_time < 120:
            # 最后1分钟线性降至0
            users = int(100 * (1 - (run_time - 60) / 60))
            return (users, 10) if users > 0 else None
        return None
```

### 5. 常见陷阱与诊断

| 现象 | 根因分析 | 解决策略 |
| :--- | :--- | :--- |
| **测试停止后控制台卡住不退出** | 某些 `on_stop` 中存在无限重试或网络超时（默认 `timeout=None`） | 为 `on_stop` 中的请求设置 `timeout=5`；使用 `--stop-timeout 30` 兜底。 |
| **`on_stop` 未执行导致资源未释放** | 进程被 `SIGKILL` 或测试超时未给足等待时间 | 在 Worker 中捕获 `signal.SIGTERM`，手动触发清理逻辑；或使用 `--stop-timeout` 强制等待。 |
| **用户退出后并发数达不到目标** | `StopUser` 退出得太快，孵化速率（`spawn-rate`）跟不上 | 提高 `spawn-rate` 值，或在业务逻辑中减少抛出 `StopUser` 的频率。 |
| **`LoadTestShape` 返回 `None` 时数据未完整上报** | 测试立即停止，最后的统计未发送至 Master | 在返回 `None` 前调用 `environment.runner.stats.write_stats_to_csv()` 手动保存。 |

### 💎 总结决策树

-   需要控制**单个用户的生命周期**？ -> 使用 `raise StopUser()`。
-   需要控制**整个测试的运行总时长**？ -> 使用 `-t` 参数 + `--stop-timeout`。
-   需要复杂的时间曲线（如阶梯升降）？ -> 编写 `LoadTestShape` 并在最后返回 `None`。

当你在分布式集群（Master-Worker）中，**永远不要在 Worker 的代码中直接调用 `sys.exit()`**，这会导致 Worker 进程直接崩溃，而 Master 无法感知业务退出原因。请一律通过 `raise StopUser()` 让 Locust 框架接管。
