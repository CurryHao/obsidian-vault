# 内存泄漏定位与长时运行稳定性优化

## Locust 内存泄漏定位与长时运行稳定性优化

内存泄漏是 Locust 长时间压测中最常见也最致命的问题之一。一个典型场景是：初始内存 200MB，运行 30 分钟后飙升至 8GB 以上，最终进程被系统 OOM Killer 杀死。本章提供系统化的定位方法论与可落地的优化方案。

---

### 一、内存泄漏的典型症状

| 症状 | 说明 |
|------|------|
| **内存持续增长** | 压测过程中内存使用率线性或阶梯式上升，不随用户数稳定而收敛 |
| **停止测试后内存不释放** | 调用 `/stop` 后内存仍居高不下，即使重新开始测试也不会进一步增加 |
| **TPS 随运行时间下降** | 内存增长到一定程度后，吞吐量显著下降（如 TPS 下降 50%） |
| **系统 OOM** | 进程因内存耗尽被系统杀死，`dmesg | grep -i kill` 可查看到 OOM 记录 |

---

### 二、根因分类与定位方法

#### 2.1 常见根因

| 根因类别 | 具体表现 | 参考案例 |
|----------|----------|----------|
| **连接池泄漏** | 每个用户实例创建独立连接池，30,000 用户消耗约 30GB 内存 | 高并发场景下内存从 200MB 增长至 8GB |
| **错误信息累积** | `resp.failure(f"Custom error: {dynamic_value}")` 产生大量独特错误条目，每个被单独存储 | 错误类型多样时消耗额外内存 |
| **响应数据未释放** | 请求大响应体后未显式关闭或释放，数据残留在内存中 | 处理大响应体时内存累积 |
| **日志堆积** | DEBUG 级别下请求日志过多，内存被日志缓存占满 | 高并发时日志 I/O 成为瓶颈 |
| **统计信息累积** | 历史统计数据未及时清理，长时间运行后膨胀 | 运行 2-3 小时后内存持续增长 |
| **Python 版本/GC 问题** | Python 3.9 及以下版本内存回收效率低 | 升级到 3.11+ 后改善明显 |

#### 2.2 定位工具链

| 工具 | 用途 | 使用方法 |
|------|------|----------|
| **`tracemalloc`** | Python 内置内存分配追踪，定位泄漏源头 | `python -X tracemalloc=25 -m locust -f locustfile.py` |
| **`memray`** | Bloomberg 开源的内存分析器，追踪 Python 代码、原生扩展和解释器内存 | `memray run --live locust -f locustfile.py` |
| **`memory_profiler`** | 逐行内存分析 | `mprof run locust -f locustfile.py` |
| **`psutil`** | 实时监控进程内存 RSS | 在测试脚本中集成 `psutil.Process().memory_info()` |
| **`objgraph`** | 查看对象引用关系，定位无法回收的对象 | `objgraph.show_growth()` |
| **`docker stats`** | 容器化部署时监控内存使用 | `docker stats <container_id>` |

#### 2.3 定位流程

``` 启动压测，使用 psutil 每 10 秒记录 RSS → 确认是否存在内存泄漏
2. 停止压测，观察内存是否回落 → 判断是"未释放"还是"持续分配"
3. 使用 tracemalloc 对比两个快照的差异 → 定位分配热点
4. 使用 objgraph 检查无法回收的对象类型 → 定位泄漏的具体对象
5. 针对性修复代码（连接池/错误处理/资源释放）
6. 重复验证
```

### 三、核心解决方案

#### 3.1 连接池优化

**问题**：每个 `HttpUser` 默认创建独立连接池，大规模并发时连接池数量爆炸。

**解决方案一：共享 Session（推荐）**

```python
from locust import HttpUser, task, between
import requests

# 全局共享 Session，所有用户复用连接池
session = requests.Session()
adapter = requests.adapters.HTTPAdapter(
    pool_connections=10,
    pool_maxsize=10,
    max_retries=0
)
session.mount('http://', adapter)
session.mount('https://', adapter)

class MyUser(HttpUser):
    def __init__(self, *args, **kwargs):
        super().__init__(*args, **kwargs)
        self.client = session  # 复用全局 Session```code`

#### 3.2 错误处理优化

**问题**：动态错误信息产生大量唯一错误条目，每个都被单独存储。

```python

```

### 四、长时运行（浸没测试）稳定性优化

浸没测试（Soak Test）通常持续数小时甚至数天，对稳定性要求极高。

#### 4.1 启动参数优化

```bash
locust -f locustfile.py \
    --headless \
    -u 1000 \
    -r 50 \
    -t 8h \
    --stop-timeout 60 \        # 优雅退出，确保资源释放
    --loglevel WARNING \
    --csv=results/soak_test \
    --stats-history-interv```code10 # 降低统计上报频率，减少内存开销
```

#### 4.2 脚本层面的稳定性设计

```python
from locust import HttpUser, task, between, events
import gc
import psutil
import logging

logger = logging.getLogger(__name__)

class SoakTestUser(HttpUser):
    wait_time = between(1, 3)
    
    def on_start(self):
        # 初始化一次，避免在 task 中重复创建对象
        self.headers = {'Content-Type': 'application/json'}
        self.payload_template = {'key': 'value'}
    
    @task
    def stable_request(self):
        # 使用预定义对象，避免重复分配
        self.client.post('/api/test', headers=self.headers, json=self.payload_template)
    
    def on_stop(self):
        # 显式关闭连接
        self.client.close()

# 定期触发 GC（每 1000 请求或每 5 分钟）
@events.request.add_listener
def periodic_gc(request_type, name, response_time, response_length, 
                response, context, exception, **kwargs):
    if kwargs.get('num_requests', 0) % 1000 == 0:
        gc.collect()
        logger.debug(f"GC triggered, memory: {psutil.Process().memory_info()```codes / 1024 / 1024:.1f}MB")
```

#### 4.3 分布式浸没测试最佳实践

| 实践 | 说明 |
|------|------|
| **Worker 数量适中** | 避免过多 Worker 导致 Master 统计聚合成为内存瓶颈 |
| **定期重启 Worker** | 对于超长测试（>12h），可考虑轮换重启 Worker（需结合 K8s 滚动更新） |
| **Master 专用高配机器** | Master 聚合所有 Worker 统计，内存需求随 Worker 数量线性增长 |
| **禁用 Web UI** | 长时运行使用 `--headless`，Web UI 本身也有内存开销 |

### 五、监控与告警

#### 5.1 关键监控指标

| 指标 | 采集方式 | 告警阈值 |
|------|----------|----------|
| **RSS 内存** | `psutil.Process().memory_info().rss` | 持续增长超过 80% 可用内存 |
| **内存增长率** | 每 5 分钟计算增量 | > 100MB/小时（浸没测试需警惕） |
| **GC 频率** | `gc.get_stats()` | 频繁 GC 且内存不降 |
| **对象数量** | `len(gc.get_objects())` | 持续增长 |

#### 5.2 内存监控脚本

```python
# memory_monitor.py - 独立运行，监控 Locust 进程
import psutil
import time
import csv
import os

def monitor_locust_memory(pid, output_file="memory_monitor.csv"):
    with open(output_file, 'w') as f:
        writer = csv.writer(f)
        writer.writerow(['timestamp', 'rss_mb', 'vms_mb', 'cpu_percent'])

                mem = proc.memory_info()

                    time.time(),

                    mem.vms / 1024 / 1024,
                    proc.cpu_percent()
                ])
                f.flush()
                time.sleep(10)
            except psutil.NoSuchProcess:
                break

### 六、优化效果参考

| 优化措施 | 优化前 | 优化后 |
|----------|--------|--------|
| 共享连接池 + 错误信息优化 | 30 分钟内存增长至 8GB | 30 分钟内存稳定在 250MB |
| Python 3.9 → Python 3.11 | GC 压力大，内存回收慢 | 内存管理效率显著提升 |
| DEBUG → WARNING 日志 | 日志缓存占用大量内存 | 内存开销大幅降低 |

---

### 七、总结

| 优先级 | 优化措施 | 预期效果 |
|--------|----------|----------|
| **P0** | 使用共享 Session/连接池 | 解决 80% 以上内存泄漏问题 |
| **P0** | 避免动态错误信息 | 防止错误条目爆炸 |
| **P1** | 使用 `with` 上下文管理器处理响应 | 确保响应数据及时释放 |
| **P1** | 升级 Python 3.11+ | 改善内存回收效率 |
| **P2** | 调整日志级别为 WARNING/ERROR | 减少日志内存开销 |
| **P2** | 长时运行定期触发 `gc.collect()` | 主动回收循环引用 |
| **P3** | 使用 `tracemalloc`/`memray` 定位泄漏 | 精准修复复杂泄漏 |

> **核心原则**：内存泄漏的根因 80% 以上集中在连接池管理和错误信息存储两个环节。优先从这两个方向入手，配合监控工具验证，即可解决绝大多数长时运行稳定性问题。
