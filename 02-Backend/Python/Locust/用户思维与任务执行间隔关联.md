# 用户思维与任务执行间隔关联

在性能测试领域，**“思考时间（Think Time）”** 是指模拟用户在两次操作之间的停顿（如浏览页面、填写表单、阅读内容）。在 Locust 中，它精准对应 **`wait_time`** 属性，直接决定了**任务执行间隔**。

理解 `wait_time` 的工作机制，是将“并发用户数”转化为“业务吞吐量（RPS）”的关键。

---

### 1. 核心关联：`wait_time` 如何控制执行间隔

在 Locust 的调度循环中，`wait_time` 决定了**当前任务结束**到**下一个任务开始**之间的间隔。

**执行时序图：**
```text
[开始] -> [执行 Task A] -> (调用 wait_time) -> [等待 N 秒] -> [执行 Task B] -> (调用 wait_time) -> [等待 N 秒] -> ...
```
**关键点**：
- **`wait_time` 不包含任务本身的执行耗时**。若任务执行耗时 2 秒，`wait_time` 设为 1 秒，则两次任务开始的时间间隔约为 3 秒。
- **`wait_time` 是“每个用户”独立计算**的，不同协程之间互不影响，因此同一时刻所有用户的等待时长分布是随机的。

---

### 2. 四种内置等待策略与适用场景

| 策略函数 | 行为逻辑 | 适用场景 |
| :--- | :--- | :--- |
| **`between(min, max)`** | 在 min 和 max 秒之间**随机均匀**选取一个值。 | **最常用**。模拟真实用户无规律的浏览行为（如 1~5 秒）。 |
| **`constant(seconds)`** | 固定等待 seconds 秒。 | 模拟定时轮询任务（如每隔 5 秒拉取一次状态）。 |
| **`constant_pacing(seconds)`** | **确保**两次任务**开始**的时间间隔**至少**为 seconds 秒。<br>若任务执行耗时 < seconds，则补足剩余时间；<br>若任务执行耗时 > seconds，则不等待，立即执行下一任务。 | **固定吞吐量场景**。模拟“每分钟固定处理 10 笔订单”的后台 Job，能有效防止任务堆积。 |
| **`constant_throughput(rate)`** | 控制每秒执行的任务数（RPS），通过动态调整等待时长实现。 | 精确限制单用户的请求速率，避免压垮下游。 |

**代码示例：**
```python
from locust import HttpUser, task, between, constant, constant_pacing, constant_throughput

class DemoUser(HttpUser):
    # 1. 随机等待 1~3 秒
    wait_time = between(1, 3)

    # 2. 固定等待 0.5 秒
    # wait_time = constant(0.5)

    # 3. 保证两次任务开始间隔至少 2 秒（若任务耗时 1.8s，则补等 0.2s；若耗时 2.5s，则不等待）
    # wait_time = constant_pacing(2)

    # 4. 单用户每秒最多执行 2 个任务
    # wait_time = constant_throughput(2)

    @task
    def work(self):
        self.client.get("/")
```

---

### 3. `between` 与 `constant_pacing` 的本质区别（关键）

这是新手最容易混淆的地方：

| 策略 | 控制的目标 | 计算公式（理想情况） | 后果 |
| :--- | :--- | :--- | :--- |
| **`between`** | **两次任务执行的“空闲间隔”** | `总间隔 = 任务耗时 + wait_time` | 若任务耗时波动大，总间隔不稳定，导致 RPS 波动。 |
| **`constant_pacing`** | **两次任务“开始执行”的时间点** | `开始间隔 ≈ max(任务耗时, pacing)` | 保证业务触发频率恒定，任务耗时再长也不会拖慢整体节奏（除非超时）。 |

**举例说明**：
- 设 `wait_time = between(1, 1)`（固定1秒），任务 A 耗时 0.1 秒，则两次任务间隔为 1.1 秒。
- 若某次任务耗时暴涨至 10 秒（数据库慢查询），则下次任务间隔变为 11 秒，**吞吐量急剧下降**。
- 若改用 `wait_time = constant_pacing(1)`，当任务耗时 10 秒时，**任务结束后不等待**，立即执行下一个任务，保证“每分钟触发次数”尽量恒定（虽然单次变慢了，但频率维持住了）。

> **实战建议**：模拟**人工操作**（如网页浏览）用 `between`；模拟**后台自动任务**（如消息队列消费）用 `constant_pacing`。

### 4. 动态 `wait_time`：根据状态自适应调整

`wait_time` 可以是一个可调用对象（函数/方法），它接收 `self` 参数，让你能根据**业务响应**动态决定下次等待多久。

```python
import random

class AdaptiveUser(HttpUser):
    def adaptive_wait(self):
        # 如果上一请求耗时较长，则增加等待时间（避免雪崩）
        last_rt = getattr(self, 'last_response_time', 100)
        return max(0.5, last_rt / 1000 * 2)  # 响应时间(ms)转秒，并放大2倍

    wait_time = adaptive_wait

    @task
    def dynamic_call(self):
        start = time.time()
        self.client.get("/")
        # 记录耗时（需在事件监听中捕获，此处仅为示意）
        self.last_response_time = (time.time() - start) * 1000
```

### 5. 作用域与继承覆盖

- **顶级 `HttpUser` 中定义**：影响该用户类的所有顶级 `@task` 和所有未单独重写 `wait_time` 的 `TaskSet`。
- **`TaskSet` 或 `SequentialTaskSet` 中重定义**：**仅影响该任务集内部的执行间隔**，进入任务集后采用新节奏，退出后恢复父级节奏。

```python
class FastTasks(TaskSet):
    # 进入此任务集后，间隔缩短至 0.2 秒
    wait_time = constant(0.2)

    @task
    def fast_api(self): self.client.get("/fast")

class MainUser(HttpUser):
    # 全局默认等待 1~5 秒
    wait_time = between(1, 5)
    tasks = {FastTasks: 1}
```

### 6. 计算关联：并发用户数 (Users) → 吞吐量 (RPS)

`wait_time` 直接决定了单个用户的 RPS 上限，公式如下：

\[
\text{单用户最大 RPS} \approx \frac{1}{\text{平均任务执行耗时} + \text{平均 wait\_time}}
\]

\[
\text{集群总 RPS} \approx \text{并发用户数} \times \text{单用户 RPS}
\]

**举例**：
- `-u 1000`（1000 用户），`wait_time = between(1,3)`（平均2秒），假设接口平均耗时 50ms。
- 单用户 RPS ≈ 1 / (0.05 + 2) ≈ **0.49** 请求/秒。
- 总 RPS ≈ 1000 × 0.49 ≈ **490 RPS**。

**启示**：如果你压测时发现 RPS 上不去，但 CPU 未跑满，大概率是 `wait_time` 设置过长。调整 `wait_time` 或减少等待时间，是提升 RPS 最直接的手段。

---

### 7. 常见陷阱与避坑指南

| 陷阱 | 现象 | 解决方案 |
| :--- | :--- | :--- |
| **任务耗时远超 `wait_time`** | 即使 `wait_time` 设为 0，RPS 依然很低（瓶颈在服务端响应慢）。 | 此时应该关注服务端的性能瓶颈，而非调整 `wait_time`。 |
| **在 `@task` 内部使用 `time.sleep()`** | 阻塞了整个 Gevent 调度器，导致其他用户无法切换，并发数急剧下降。 | **绝对禁止**。必须使用 `wait_time` 机制（底层调用 `gevent.sleep`）。 |
| **所有用户的 `wait_time` 完全一样（固定值）** | 出现“共振”现象，所有用户在相同时间点发起请求，导致流量毛刺。 | 默认使用 `between` 引入随机性，避免同步冲击。 |
| **混淆 `between` 和 `constant_pacing` 的语义** | 测试结果不符合预期吞吐量。 | 思考：你要的是“空闲间隔随机”还是“触发频率恒定”？前者用 `between`，后者用 `pacing`。 |

---

### 💎 总结

- **思考时间（`wait_time`）是连接“用户数”和“请求量”的桥梁**，通过它你可以精准调教压测流量模型。
- **`between`** 适合仿真人机交互；**`constant_pacing`** 适合仿真机器任务流。
- **动态 `wait_time`** 是实现自适应负载的高级手段，能有效避免压测工具自身成为“雪崩推手”。
