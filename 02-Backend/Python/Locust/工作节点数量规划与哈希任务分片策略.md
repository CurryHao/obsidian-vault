# 工作节点数量规划与哈希任务分片策略

在进行大规模分布式压测时，**工作节点（Worker）的数量规划**和**任务分片策略**是决定压测结果是否准确、资源是否浪费的关键。这不仅仅是“启动几个 `--worker`”的问题，更涉及**目标系统容量**、**压测机性能**以及**数据一致性**的综合权衡。

下面我将从**容量规划公式**、**哈希分片原理**以及**实战策略**三个维度为你拆解。

---

### 1. Worker 数量规划：从“目标 RPS”反推

压测集群的总吞吐量（RPS）由所有 Worker 共同贡献。规划 Worker 数量的核心公式如下：

**总 RPS = Worker数量 × 单Worker最大RPS**

#### A. 单 Worker 最大 RPS 如何估算？
- **理论值**：在最佳条件下（`wait_time=0`，接口响应极快），一个 `FastHttpUser` 进程（单核）可处理约 **16,000 RPS**（官方数据）。
- **实际值**：受限于：
  - **接口响应时间（RT）**：RT 越长，单 Worker RPS 越低。公式：`单Worker RPS ≈ 协程数 / (RT + wait_time)`
  - **Python GIL**：单进程只能跑满 1 个 CPU 核心。
  - **网络带宽**：若响应体较大（如 1MB），带宽会先于 CPU 成为瓶颈。

**实战估算表**（以 FastHttpUser 为例）：

| 场景 | 接口 RT | 单 Worker 并发数 | 估算 RPS | 建议 Worker 数（目标 10万 RPS） |
| :--- | :--- | :--- | :--- | :--- |
| **纯文本/小数据** | 10ms | 500 | ~8,000 | 13 个 |
| **中等负载** | 50ms | 500 | ~3,000 | 34 个 |
| **大数据/慢接口** | 200ms | 500 | ~800 | 125 个 |

> **瓶颈排查**：若增加 Worker 后总 RPS 不升反降，说明 Master 的统计聚合已成为瓶颈（单核 CPU 满载），需考虑 `--processes` 或升级 Master 硬件。

---

### 2. 任务分片策略：为什么要“哈希分片”？

在分布式压测中，最棘手的不是“产生压力”，而是**“数据不冲突”**。例如：
- 10 个 Worker 同时用 `user_001` 登录，会导致 Token 互踢。
- 多个 Worker 同时扣减同一个库存，导致数据不一致。

**哈希分片**的核心思想是：**将“业务主键”（如用户 ID、订单号）通过哈希算法，映射到固定的 Worker**，确保同一个业务实体始终由同一个 Worker 处理。

#### A. 方案一：在 Worker 端预取数据分片（静态分配）
这是最常用的方法：在 `test_start` 阶段，让每个 Worker 根据自身 IP 或 ID，从全局数据池中**领取专属的数据范围**。

```python
# worker_data_loader.py
import hashlib
from locust import events
from locust.runners import WorkerRunner

@events.test_start.add_listener
def load_data_shard(environment, **kwargs):
    if not isinstance(environment.runner, WorkerRunner):
        return
    
    # 获取 Worker 的唯一标识（如 IP + 进程ID）
    worker_id = environment.runner.client_id
    # 假设总账号池 100 万个，10 个 Worker
    total_users = 1000000
    total_workers = 10
    
    # 根据 worker_id 的哈希值取模，分配数据区间
    shard_index = int(hashlib.md5(worker_id.encode()).hexdigest(), 16) % total_workers
    chunk_size = total_users // total_workers
    start = shard_index * chunk_size
    end = start + chunk_size
    
    # 从 Redis 或 CSV 中只加载属于该区间的账号
    global ACCOUNT_POOL
    ACCOUNT_POOL = load_users_from_range(start, end)
    print(f"[Worker {worker_id[:8]}] 分配到账号区间: {start}-{end}")
```
**适用场景**：数据规模大，且数据量在测试前已知（如 CSV 文件）。

#### B. 方案二：Master 端哈希路由（动态分发）
当业务请求的“目标对象”不固定时（如随机用户登录），可以在 Master 端根据请求参数计算哈希，将任务指定给特定的 Worker。这需要借助 **`events.worker_report`** 或自定义消息实现。

```python
# Master 端路由逻辑（伪代码）
@events.worker_report.add_listener
def route_task(environment, client_id, data, **kwargs):
    if "user_id" in data:
        # 根据 user_id 取模，决定由哪个 Worker 执行
        target_worker = hash(data["user_id"]) % len(environment.runner.clients)
        # 将该任务发送给目标 Worker（需自定义消息，本例略）
```

**适用场景**：需要模拟“有状态”业务，且用户 ID 动态生成。

#### C. 方案三：使用 Redis 全局分布式锁（低效，不推荐）
若无法分片，只能在更新库存等关键操作时使用 Redis 原子操作（如 `DECR`），但这会引入额外网络延迟，且无法消除“数据热点”问题。

### 3. 高级策略：结合 `--expect-workers` 实现弹性分片

当 Worker 数量不确定（如 K8s 自动扩缩容）时，可以在 `test_start` 中通过 `environment.runner.clients` 获取当前在线 Worker 列表，动态计算分片。

```python
@events.test_start.add_listener
def dynamic_sharding(environment, **kwargs):
    if isinstance(environment.runner, MasterRunner):
        # Master 计算分片方案并广播给所有 Worker
        workers = list(environment.runner.clients.keys())
        for idx, worker_id in enumerate(workers):
            shard_config = {"worker_id": worker_id, "shard_index": idx, "total": len(workers)}
            # 通过自定义消息发送给 Worker（需扩展）
            send_to_worker(worker_id, shard_config)
```

### 4. 关键陷阱与最佳实践

| 陷阱 | 后果 | 解决方案 |
| :--- | :--- | :--- |
| **Worker 数超过目标系统连接数上限** | 大量连接被拒绝，失败率飙升。 | 规划前先了解目标系统的最大连接数（如 Nginx `worker_connections`）。 |
| **哈希分片不均匀（数据倾斜）** | 某些 Worker 压力过大，其他闲置。 | 使用更均匀的哈希函数（如 `murmurhash`），或在分配前对数据做随机打散（shuffle）。 |
| **动态扩缩容导致分片重新分配** | Worker 间数据迁移复杂，易出错。 | 固定 Worker 数量，或在设计初期就使用“无状态”请求（如只读查询）。 |
| **Master 聚合成为瓶颈** | 100 个 Worker 同时上报数据，Master CPU 100%。 | 增加 `--stats-interval`（如 10 秒），减少聚合频率。 |
| **Worker 内存溢出（OOM）** | 每个 Worker 加载全量数据（如 10GB CSV）。 | 只加载分片数据，或使用 `mmap` 内存映射文件。 |

### 5. 实战决策树

```text
问题：我要压测多少 RPS？ -> 反推 Worker 数量
    |
    如果数据有状态（如登录态）？
    |--- 是：采用哈希分片，绑定数据到固定 Worker
    |       |--- 数据静态（CSV）？ 用 Worker 端预取分片
    |       |--- 数据动态（API）？ 用 Master 端哈希路由
    |
    如果数据无状态（如查询天气）？
        |--- 无需分片，任意 Worker 均可执行，只需注意全局 `wait_time` 独立计算即可。
```

---

### 💎 总结

- **Worker 数量** = **目标 RPS / 单 Worker 估算 RPS**，同时受限于目标系统的连接数上限。
- **哈希分片**是解决“分布式数据冲突”的成熟方案，优先在 Worker 端预取数据区间（静态分配）。
- **动态扩缩容**场景下，务必在 `test_start` 中实时计算分片方案，确保一致性。
- **黄金法则**：**先做小规模测试（2~3 个 Worker），验证分片逻辑正确性，再放大到生产级规模。**
