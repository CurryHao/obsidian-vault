# 实时折线图与百分位数分析

在 Locust 的 Web 仪表盘中，**实时折线图（Charts）** 和 **百分位数（Percentiles）** 是分析系统性能**动态变化趋势**的核心工具。与静态的数字表格不同，折线图能揭示系统在时间轴上的**稳定性**和**劣化拐点**。

下面我将带你穿透图表表象，掌握通过曲线形态诊断性能瓶颈的方法。

---

### 1. 实时折线图（Charts）的核心解读

在 Locust Web UI 的 **Charts** 选项卡下，有四个核心折线图。解读时，请务必将其**串联起来看**，而非孤立分析。

#### A. 总请求数/秒（Total Requests per Second）
-   **解读**：衡量系统当前的吞吐量。
-   **健康曲线**：随着并发用户数（Users）爬升，RPS 应同步线性上升，最终在系统资源饱和时趋于**平稳（平台期）**。
-   **危险信号**：
    -   **RPS 骤降（悬崖式下跌）**：通常意味着系统出现严重错误（如连接池耗尽、数据库死锁），大量请求超时，导致有效吞吐量急剧下降。
    -   **RPS 剧烈震荡（锯齿形）**：说明系统存在频繁的 GC（垃圾回收）或定时任务干扰，或者系统在反复触发限流熔断。

#### B. 响应时间（Response Time，含 Average/Median/95th/99th）
-   **解读**：这是最关键的趋势图，通常包含多条颜色不同的曲线。
-   **理想状态**：所有曲线**平坦如水平线**，不随 RPS 增加而显著爬升。
-   **关键拐点**：当某条曲线开始**向上翘起（拐点）**，说明系统已达到性能瓶颈，请求开始排队等待。

#### C. 用户数（Users）
-   **解读**：显示当前实际活跃的虚拟用户数（协程数）。
-   **联动分析**：若 **User 曲线**已达到设定的目标值（如 1000），但 **RPS 曲线**仍在缓慢爬升，说明 `wait_time` 和思考时间占据了主导，系统压力尚未完全释放；若 User 曲线频繁无法达到目标值，则说明压测机（Worker）自身的 CPU 已饱和。

#### D. 失败数（Failures per Second）
-   **解读**：每秒发生的错误数。
-   **高能预警**：一旦失败曲线出现**持续的脉冲**（哪怕失败率只有 1%），说明系统已处于不稳定状态，此时观察到的响应时间数据已无参考价值（因为成功处理的请求都是“幸存者偏差”）。

---

### 2. 百分位数（Median/95th/99th）的深度剖析

为什么必须看百分位数，而不是只看平均值（Avg）？因为**平均值会掩盖长尾延迟**。

#### A. 定位与含义
-   **Median（中位数，P50）**：**体感基准线**。表示 50% 的用户体验到的响应时间。如果 P50 都很高，说明系统存在普遍性慢查询。
-   **95th Percentile（P95）**：**SLA 核心红线**。表示 95% 的用户体验到的响应时间。**99% 的性能测试 SLA 都以此指标作为评判标准**，因为它剔除了 5% 的极端波动，反映了“大多数较差情况”下的体验。
-   **99th Percentile（P99）**：**长尾延迟侦察兵**。表示 1% 的最差情况。用于排查磁盘 I/O 抖动、GC 停顿、网络丢包重传等问题。

#### B. 三条曲线的组合诊断（动态分析）

| 曲线关系 | 诊断结论 | 常见根因 |
| :--- | :--- | :--- |
| **三者紧密贴合**（Med ≈ P95 ≈ P99） | 系统响应极其**稳定**，无抖动。 | 系统资源充裕，处理逻辑简单（如纯内存缓存）。 |
| **Med 低，P95 高**（差值 > 2x） | 存在**中度长尾延迟**，少数用户卡顿。 | 数据库存在慢 SQL、缓存穿透、或部分热点 Key 访问不均。 |
| **Med 低，P99 极高**（偶发巨峰） | 存在**极少数瞬时卡顿**。 | Java 应用发生 Full GC、网络重传、或服务器 CPU 节流（Throttling）。 |
| **Med 和 P95 平稳，但 P99 持续**上升 | **长尾趋势恶化**，即将演变为普遍性问题。 | 线程池队列逐渐积压，或内存泄漏导致 GC 频率加快。 |

---

### 3. 结合场景：实时曲线的“健康模式”速查

通过观察折线图的形态，你可以快速定位系统处于哪个阶段：

| 曲线特征 | 阶段判定 | 行动建议 |
| :--- | :--- | :--- |
| **RPS 随 Users 线性上升，响应时间曲线平坦** | **绿色健康** | 系统有余量，可继续加压直至找到上限。 |
| **RPS 开始变平，响应时间曲线开始微翘** | **性能拐点（瓶颈临界）** | 此时即为系统的最大容量点。停止加压，分析服务端 CPU/DB 连接数。 |
| **RPS 开始**下降 **，响应时间曲线飙升** | **系统过载/崩溃** | 立即停止压测！此时系统正在“濒死挣扎”，内部队列已满。检查是否触发了限流或死锁。 |
| **响应时间曲线呈现**周期性波浪 **（正弦波）** | **定时任务干扰** | 检查目标服务器的定时 Cronjob（如日志切割、数据备份）。 |

---

### 4. 分布式环境下的特殊警示

在分布式（Master-Worker）模式下查看 Charts 时，需要注意一个陷阱：

-   **统计聚合延迟**：Charts 展示的是 Master 聚合后的数据。如果网络延迟较高，或 Worker 上报间隔（默认 3 秒）较长，图表会出现**“阶梯状”或“滞后”**现象，导致高并发下的瞬间毛刺被“抹平”。
-   **应对**：若观察 P99 时发现与预期不符，请结合 `--csv` 导出的详细数据（精度到毫秒）进行二次验证，不要仅依赖 Web 实时图表的渲染精度。

---

### 5. 实战排查示例（通过曲线讲故事）

**场景复现**：你正压测一个电商下单接口。
1.  **前 30 秒**：Users 从 0 升至 500，RPS 同步升至 1000，Median/P95/P99 均稳定在 20ms。**结论：正常。**
2.  **第 30-45 秒**：Users 升至 1000，RPS 仅升至 1200，**P95 从 30ms 升至 200ms**。**结论：系统出现 CPU/DB 瓶颈。**
3.  **第 50 秒**：P95 飙升至 2000ms，Failures 曲线出现脉冲（ConnectionError）。**结论：连接池耗尽，系统已不可用。**

这种**“RPS 滞涨 → P95 率先突破阈值 → 失败率伴随出现”**的曲线演变，是性能测试中最经典的崩溃前兆。熟练捕捉这个信号，你就能在系统真正雪崩前精准停止压测，获取宝贵的瓶颈样本。
