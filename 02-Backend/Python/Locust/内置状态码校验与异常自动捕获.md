# 内置状态码校验与异常自动捕获

在 Locust 中，**状态码校验**与**异常捕获**的自动化程度，是区分其与普通 `requests` 脚本的重要标志。Locust 默认将“网络层错误”和“HTTP 错误状态码”**自动归入失败统计**，让你无需编写繁琐的 `if` 判断就能获得准确的压测结果。

但理解其底层机制——特别是 `HttpUser` 与 `FastHttpUser` 的差异——能帮助你在面对业务失败（如返回 `{"code":500}` 但 HTTP 状态码为 200）时，精准地使用 `catch_response` 进行覆盖。

---

### 1. 默认行为：双轨制自动捕获

Locust 默认会从**两个维度**自动判定请求是否失败，并分别计入 Web UI 的 **Failures** 和 **Exceptions** 选项卡。

| 判定维度 | 触发条件 | 统计归属 | 是否自动重试 |
| :--- | :--- | :--- | :--- |
| **HTTP 状态码** | 响应码 >= 400 | **Failures**（失败数） | 否 |
| **网络/协议异常** | 连接超时、连接拒绝、TLS 握手失败 | **Exceptions**（异常数） | 否 |

```text
# Web UI 中你会看到：
Type     Name                # Requests    # Failures    Median Response Time
GET      /api/order          1,000         5 (0.5%)     120ms
         (其中 5 个是 500 错误，自动计入 Failures)
```


### 2. `HttpUser` vs `FastHttpUser` 的底层捕获逻辑差异（关键）

| 特性                        | **`HttpUser` (基于 `requests`)**                                     | **`FastHttpUser` (基于 `geventhttpclient`)**                                        |
| :------------------------ | :----------------------------------------------------------------- | :-------------------------------------------------------------------------------- |
| **状态码 4xx/5xx**           | **不抛异常**，返回 `Response` 对象。Locust 框架检查 `resp.status_code` 并自动标记为失败。 | **默认抛异常**（`HTTPError`）。Locust 捕获异常并计入 `Exceptions`。                               |
| **网络异常**（超时/DNS）          | 抛出 `requests.exceptions.Timeout` 等，被 Locust 捕获。                    | 抛出 `geventhttpclient.exceptions.Timeout` 等，被 Locust 捕获。                           |
| **`catch_response` 下的行为** | 需手动 `resp.success()` / `resp.failure()`，框架不再自动判定状态码。               | 需手动 `resp.success()` / `resp.failure()`，框架不再自动判定状态码。                              |
| **关键配置**                  | 无特殊配置。                                                             | **`raise_on_error`** 参数：默认为 `True`（抛异常）。若设为 `False`，则行为同 `HttpUser`（不抛异常，框架标记失败）。 |

**实战建议**：
- 若你希望所有 4xx/5xx 统一显示在 **Failures** 中（而非 Exceptions），在 `FastHttpUser` 中设置 `raise_on_error = False`。
- 若你希望区分“网络问题”和“业务拒绝”，则保持默认，4xx/5xx 进入 Exceptions，连接错误也进入 Exceptions（但可通过异常类型区分）。

```python
from locust import FastHttpUser

class MyUser(FastHttpUser):
    # 让 FastHttpUser 像 HttpUser 一样，将 4xx/5xx 作为普通失败统计，而非抛异常
    raise_on_error = False
```

### 3. 使用 `catch_response=True` 覆盖自动校验（业务逻辑失败）

当接口返回 HTTP 200，但业务字段 `code != 0` 时，必须使用 `catch_response` 手动标记失败。

```python
@task
def create_order(self):
    with self.client.post("/order", json={"product": "book"}, catch_response=True) as resp:
        # 即使 status_code 是 200，框架也不会自动标记成功
        if resp.status_code == 200:
            data = resp.json()
            if data.get("code") == 0:
                resp.success()   # 手动标记成功
            else:
                resp.failure(f"业务错误: {data.get('msg')}")  # 标记失败，计入 Failures
        else:
            # 对于 4xx/5xx，catch_response 下框架不会自动标记，需手动处理
            resp.failure(f"HTTP 错误: {resp.status_code}")
```

**关键点**：一旦启用 `catch_response`，**所有状态码**（包括 200）都不会自动判定，必须显式调用 `resp.success()` 或 `resp.failure()`。

---

### 4. 捕获并处理网络层异常（超时/连接拒绝）

在使用 `catch_response` 时，网络层异常（如超时）**不会被 `with` 块捕获**，需要在外部用 `try-except` 处理，或依赖 Locust 全局自动捕获。

```python
@task
def fragile_api(self):
    try:
        with self.client.get("/unstable", catch_response=True, timeout=3) as resp:
            if resp.status_code == 200:
                resp.success()
            else:
                resp.failure(f"HTTP {resp.status_code}")
    except Exception as e:
        # 捕获超时、连接错误等（这些异常 Locust 会自动统计，但不会执行到 with 块内部）
        # 手动上报失败（若不处理，Locust 会将其计入 Exceptions，而这里我们可以选择转为 Failures）
        self.environment.events.request.fire(
            request_type="GET",
            name="/unstable",
            response_time=0,
            response_length=0,
            exception=e,
            context={}
        )
        # 可选：退出用户
        # raise StopUser()
```

### 5. 全局异常监听与日志（`@events.request`）

若需要在异常发生时执行自定义逻辑（如打印日志、发送告警），可使用监听器。

```python
from locust import events

@events.request.add_listener
def on_request(request_type, name, response_time, response_length, response, exception, context, **kwargs):
    if exception:
        # 所有异常都会进入这里（包括状态码 4xx/5xx 抛出的 HTTPError）
        print(f"[ERROR] {name} 失败: {exception}")
        # 可在此处记录到外部日志系统
```

### 6. `HttpUser` vs `FastHttpUser` 异常类型对比（调试参考）

| 客户端 | 超时异常 | 连接异常 | HTTP 错误异常 |
| :--- | :--- | :--- | :--- |
| **HttpUser** | `requests.exceptions.Timeout`<br>`requests.exceptions.ConnectTimeout`<br>`requests.exceptions.ReadTimeout` | `requests.exceptions.ConnectionError` | **不抛异常**（仅返回响应对象） |
| **FastHttpUser**<br>(`raise_on_error=True`) | `geventhttpclient.exceptions.Timeout` | `geventhttpclient.exceptions.ConnectionError` | `geventhttpclient.exceptions.HTTPError`<br>（状态码 >= 400） |

### 7. 自动重试机制（借助 `catch_response` 手动实现）

Locust **不内置自动重试**，但可以封装一个装饰器或方法实现重试逻辑，且不影响统计准确性。

```python
def retry_request(func):
    def wrapper(self, *args, **kwargs):
        max_retries = kwargs.pop('retries', 3)
        for attempt in range(max_retries):
            with func(self, *args, catch_response=True, **kwargs) as resp:
                if resp.status_code < 500:
                    resp.success()
                    return
                # 5xx 错误，等待后重试
                gevent.sleep(2 ** attempt)
                resp.failure(f"重试 {attempt+1} 次失败")
        # 最终失败
    return wrapper

@task
@retry_request
def flaky_post(self):
    return self.client.post("/flaky", json={...})
```

### 8. 核心陷阱与最佳实践

| 陷阱 | 表现 | 解决方案 |
| :--- | :--- | :--- |
| **`FastHttpUser` 默认 4xx 计入 Exceptions** | Web UI 中 Failures 少，Exceptions 多，难以区分。 | 若希望统一为 Failures，设置 `raise_on_error=False`。 |
| **忘记在 `catch_response` 中调用 `success()`** | 请求永远不会被标记为成功或失败，在 Web UI 中显示为 **“未统计”**，导致总请求数异常。 | 务必在所有分支（包括异常分支）调用 `success()` 或 `failure()`。 |
| **`catch_response` 块内未捕获网络异常** | 超时异常导致 `with` 块提前退出，无法执行 `resp.failure()`。 | 使用 `try-except` 包裹 `with` 块，并手动上报事件（或依赖全局自动统计）。 |
| **业务码失败但未 `catch_response`** | 接口返回 200，但 `code=500`，Locust 认为成功，压测报告“零失败”但业务实际全挂。 | 对所有关键接口（如下单、支付）强制使用 `catch_response` 校验业务码。 |
| **重试导致统计失真** | 重试成功和失败都计入统计数据，难以区分真实成功率。 | 推荐将重试逻辑封装在 `try` 内，**最终只上报最后一次结果**，或在 `name` 中标注 `retry` 区分。 |

---

### 💎 总结

- **默认校验**：HTTP 状态码 >= 400 自动失败（HttpUser）或抛异常（FastHttpUser），网络异常自动捕获。
- **业务校验**：**必须使用 `catch_response=True`** 手动标记 `success()` / `failure()`，否则 200+错误码会被误判为成功。
- **行为统一**：若希望 `FastHttpUser` 与 `HttpUser` 行为完全一致（4xx/5xx 计入 Failures），设置 `raise_on_error = False`。
- **黄金法则**：对于涉及资金、库存、用户状态的接口，永远不要依赖默认的状态码校验。
