# 文件上传与二进制流处理

在 Locust 中进行文件上传压测，是模拟用户提交表单、上传头像、导入数据等场景的必备技能。这涉及**`multipart/form-data`（混合表单）**和**`application/octet-stream`（纯二进制流）**两种截然不同的处理方式。

核心挑战在于**内存管理**：如果每个协程都加载大文件到内存，压测机本身会先于目标服务崩溃。同时，`HttpUser` 与 `FastHttpUser` 在该场景下的 API 支持差异极大，选错会导致脚本根本无法运行。

---

### 1. `multipart/form-data`：表单 + 文件混合上传

这是最常见的场景（如上传头像 + 用户ID）。关键在于区分**表单字段**和**文件字段**。

#### A. `HttpUser`：使用 `files` 参数（原生支持，最易用）
`HttpUser` 底层基于 `requests`，支持 `files` 参数，自动处理 `Content-Type` 和边界（boundary）。

```python
from locust import HttpUser, task
import os

class UploadUser(HttpUser):
    # 共享内存中的数据（避免反复读盘）
    _image_data = None

    def on_start(self):
        # 只读一次文件到内存（所有用户共享只读数据）
        if UploadUser._image_data is None:
            with open("test_avatar.jpg", "rb") as f:
                UploadUser._image_data = f.read()

    @task
    def upload_avatar(self):
        # 方式一：简单文件上传（无额外字段）
        files = {"file": ("avatar.jpg", self._image_data, "image/jpeg")}
        self.client.post("/upload", files=files)

    @task
    def upload_with_metadata(self):
        # 方式二：混合表单字段 + 文件
        files = {
            "file": ("report.pdf", self._image_data, "application/pdf"),
            # 注意：这里的 "user_id" 是表单字段，放在 data 中，不要放在 files 里
        }
        data = {
            "user_id": str(self.user_id),
            "category": "profile"
        }
        self.client.post("/upload_meta", files=files, data=data)

    @task
    def upload_multiple_files(self):
        # 方式三：多个文件（键名相同或不同）
        files = [
            ("images", ("img1.jpg", self._image_data, "image/jpeg")),
            ("images", ("img2.jpg", self._image_data, "image/jpeg")),
        ]
        self.client.post("/batch_upload", files=files)
```
## B. `FastHttpUser`：**不支持 `files` 参数**（需手动构建）
`FastHttpUser` 底层使用 `geventhttpclient`，它是一个轻量级客户端，**没有** `files` 参数。你必须手动构造 `multipart` 请求体并计算 `Content-Length`。

**推荐方案**：使用 `requests_toolbelt` 的 `MultipartEncoder`（它生成流式编码器，且能自动计算长度）或手动拼接字节。

```python
from locust import FastHttpUser, task
from requests_toolbelt.multipart.encoder import MultipartEncoder

class FastUploadUser(FastHttpUser):
    _image_data = None

    def on_start(self):
        if FastUploadUser._image_data is None:
            with open("test.png", "rb") as f:
                FastUploadUser._image_data = f.read()

    @task
    def upload_manually(self):
        # 1. 构建 multipart 编码器（内存中生成，但可迭代）
        encoder = MultipartEncoder(
            fields={
                "user_id": str(self.user_id),
                "file": ("photo.png", self._image_data, "image/png")
            }
        )

        # 2. 设置正确的 Content-Type（包含 boundary）
        headers = {"Content-Type": encoder.content_type}

        # 3. 发送请求（body 可以是编码器对象，它实现了 read()）
        # 注意：FastHttpUser 的 client.post 接受 bytes 或 file-like 对象
        self.client.post(
            "/upload",
            data=encoder,  # 流式读取
            headers=headers
        )
```

> **内存风险**：若文件极大（>10MB），`MultipartEncoder` 仍会占用内存。极大型文件建议直接使用文件对象（`open` 返回的句柄）传给 `data`，配合分块传输。

### 2. 纯二进制流（`application/octet-stream`）

这种场景常用于上传原始数据（如日志文件、数据库备份）。此时不关心表单字段，直接发送原始字节。

```python
# HttpUser 和 FastHttpUser 通用写法
class BinaryUploadUser(HttpUser):
    def on_start(self):
        # 缓存二进制数据
        self.bin_data = b"\x00\x01\x02" * 1024 * 1024  # 1MB 模拟数据

    @task
    def upload_binary(self):
        headers = {"Content-Type": "application/octet-stream"}
        self.client.post(
            "/binary",
            data=self.bin_data,
            headers=headers,
            name="/binary_upload"
        )
```

### 3. 内存优化：避免“每个协程复制一份文件”

**反模式**：在 `on_start` 中 `open(file, "rb").read()` 并赋值给 `self.file_data`。如果有 1000 个用户，内存中将存在 1000 份相同的大文件副本，极易导致 OOM（内存溢出）。

**正确策略**（生产级）：
1. **类变量共享只读数据**（如上面的 `_image_data = None`）：所有用户共享同一份字节数据，只读安全。
2. **使用文件句柄流式传输**：对于 >10MB 的大文件，不读入内存，直接传递文件对象（需注意 `seek` 重置）。

```python
class StreamingUploadUser(HttpUser):
    @task
    def upload_large_file(self):
        with open("huge_video.mp4", "rb") as f:
            # 注意：requests 库会读取整个文件到内存吗？
            # 对于 HttpUser：requests 默认会读取整个文件到内存，除非使用生成器。
            # 对于 FastHttpUser：geventhttpclient 支持传入文件对象并分块读取。
            
            # 最佳实践：对于 HttpUser，手动分块流式上传
            # 使用 data 生成器
            def file_generator():
                with open("huge_video.mp4", "rb") as f2:
                    while chunk := f2.read(8192):
                        yield chunk
            
            self.client.post("/upload_large", data=file_generator())
```

**更高级的做法**：生成**合成数据**（如 `os.urandom(1024*1024)`）替代读取真实文件，避免磁盘 I/O 成为瓶颈。

### 4. 关键性能陷阱与超时设置

| 陷阱 | 后果 | 解决方案 |
| :--- | :--- | :--- |
| **超大文件全量加载** | 压测机内存爆满，触发 OOM Killer。 | 使用类变量共享只读数据，或流式传输。 |
| **上传请求超时过长** | 协程长期占用，有效并发数下降。 | 设置 `timeout` 为较大值（如 120s），并配合 `--stop-timeout` 兜底。 |
| **`FastHttpUser` 误用 `files`** | 脚本抛出 `TypeError: got unexpected keyword argument`。 | 切换为手动 `MultipartEncoder` 或改用 `HttpUser`。 |
| **Content-Length 不匹配** | 服务端接收数据截断或超时。 | 使用 `MultipartEncoder` 自动管理长度；若手动拼接，务必计算准确。 |
| **磁盘 I/O 争抢** | 大量协程同时读取同一文件，导致 CPU 等待（wa 升高）。 | 将文件放入内存盘（`/dev/shm`）或使用 `io.BytesIO` 生成虚拟数据。 |

### 5. 高级技巧：模拟“进度条”与分块上传（Chunked）

部分场景涉及分块上传。此时需将文件切片，并发起多次 `PUT` 请求，需在 `SequentialTaskSet` 中管理状态。

```python
from locust import SequentialTaskSet, task

class ChunkUploadFlow(SequentialTaskSet):
    def on_start(self):
        self.file_data = b"0" * (1024 * 1024 * 10)  # 10MB
        self.chunk_size = 1024 * 1024  # 1MB per chunk
        self.total_chunks = len(self.file_data) // self.chunk_size
        self.upload_id = None

    @task
    def init_upload(self):
        resp = self.client.post("/upload/init", json={"size": len(self.file_data)})
        self.upload_id = resp.json()["upload_id"]

    @task
    def upload_chunks(self):
        # 注意：顺序执行，依赖 self.upload_id
        for i in range(self.total_chunks):
            chunk = self.file_data[i*self.chunk_size:(i+1)*self.chunk_size]
            self.client.put(
                f"/upload/{self.upload_id}/chunk/{i}",
                data=chunk,
                headers={"Content-Type": "application/octet-stream"}
            )
        self.interrupt()
```

### 6. 终极决策表：该用哪种方案？

| 场景描述 | 推荐 User 类型 | 数据传递方式 | 关键 Headers |
| :--- | :--- | :--- | :--- |
| **小文件 + 表单字段**（<1MB） | `HttpUser` | `files` 参数 + `data` 参数 | 自动生成 |
| **小文件 + 表单字段**（<1MB, 追求极致性能） | `FastHttpUser` | `requests_toolbelt.MultipartEncoder` | `encoder.content_type` |
| **纯二进制上传**（无字段） | 任意 | `data=bytes` | `application/octet-stream` |
| **超大文件**（>50MB） | `FastHttpUser` 或 `HttpUser` + 生成器 | 文件对象 或 生成器（yield chunks） | 建议设置 `Transfer-Encoding: chunked`（若服务端支持） |
| **避免磁盘 I/O** | 任意 | `data=os.urandom(1024*1024)` | 无需，置于内存中 |

---

### 💎 总结

1. **小文件用 `HttpUser` + `files`**，开发效率最高，代码最简洁。
2. **追求吞吐量用 `FastHttpUser`**，但必须用第三方库（如 `requests_toolbelt`）手动构建 `multipart`，且需注意 `gevent` 兼容性（`MultipartEncoder` 是纯 Python 实现，兼容良好）。
3. **永远不要**在 `on_start` 中将大文件绑定到 `self`，除非你只有 10 个并发。**类变量共享只读数据**是标准做法。
4. 配合 **`--max-rps`** 限制总上传速率，避免瞬间打满目标服务器的带宽或磁盘队列。
