# 等待时间与并发用户数（users）的协同关系

理解 **等待时间（`wait_time`）** 与 **并发用户数（`users`）** 的协同关系，是性能测试从“盲猜”走向“精准控制”的分水岭。二者共同决定了压测的**总吞吐量（RPS）**，但角色截然不同：**`users` 决定“有多少人同时干活”**，**`wait_time` 决定“每个人干活的快慢”**。

---

### 1. 核心数学纽带：Little's Law 变体

在 Locust 中，总请求吞吐量（RPS）的数学期望为：

\[
\text{总 RPS} \approx \frac{\text{并发用户数}(users)}{\text{平均任务总耗时}}
\]

其中 **平均任务总耗时 = 平均接口响应时间 (RT) + 平均等待时间 (wait_time)**

**关键洞察**：
- **`users` 是分子**：线性放大 RPS。
- **`wait_time` 是分母的一部分**：非线性调节 RPS（因为它与 RT 相加）。

---

### 2. 角色分工：谁主“并发”，谁主“频率”

| 维度 | **并发用户数 (`users`)** | **等待时间 (`wait_time`)** |
| :--- | :--- | :--- |
| **控制对象** | **系统资源占用**（同时存在的协程数量） | **单用户行为节奏**（两次任务的空闲间隔） |
| **影响 RPS 的方式** | **线性乘数效应**（增加 1 倍用户，RPS 约增加 1 倍） | **倒数效应**（等待时间减半，单用户 RPS 翻倍） |
| **主要限制** | 受限于压测机内存/CPU 以及目标服务器的连接数 | 受限于业务真实性和目标服务器处理能力 |
| **典型调整场景** | 想增加总压力时优先调整 | 想改变请求分布或模拟不同用户类型时调整 |

---

### 3. 深度协同：四种经典组合策略

#### A. 增加 `users` + 保持 `wait_time` 不变（线性扩容）
- **效果**：RPS 与用户数成正比上升。
- **公式**：`新RPS = 旧RPS × (新users / 旧users)`
- **适用**：验证系统水平扩展能力（如加机器是否能扛住翻倍流量）。

#### B. 保持 `users` 不变 + 缩短 `wait_time`（提升频率）
- **效果**：单用户单位时间内的请求数增加，总 RPS 上升，但并发数未变。
- **适用**：模拟用户操作速度加快（如“双十一”秒杀场景中用户疯狂点击）。
- **风险**：单用户 RPS 过高可能导致客户端本地端口耗尽或 CPU 飙升。

#### C. 增加 `users` + 同时增加 `wait_time`（弹性缓冲）
- **效果**：总 RPS 可能变化不大，但系统维持的**长连接数**增加。
- **适用**：测试数据库连接池、WebSocket 长连接容量或内存占用。你增加了用户，但他们都在“思考”，不发起请求，只看系统能否撑住这么多空闲会话。

#### D. 保持 `users` 不变 + 动态调整 `wait_time`（自适应背压）
- **效果**：根据服务器响应时间（RT）反向调节等待时间，实现“智能避震”。
- **公式**：`wait_time = max(0, target_interval - actual_RT)`
- **适用**：模拟真实用户在页面卡顿时会停下来等待，而非疯狂重试。

---

### 4. 关键陷阱：`wait_time` 过长会“吞掉”用户数

**误区**：认为 `-u 1000` 一定能产生每秒 1000 个请求。
**真相**：若 `wait_time = between(5, 10)`（平均 7.5s），接口 RT = 50ms（0.05s）。
- 单用户 RPS ≈ `1 / (7.5 + 0.05) ≈ 0.132`
- 总 RPS ≈ `1000 × 0.132 ≈ 132 RPS`

此时，即使你将 `users` 从 1000 提升到 2000，RPS 也只能达到 264。**压测工具的资源被“思考时间”吃掉了，并没有转化为有效请求压力。**

> **实战法则**：如果你想要 1000 RPS，有两种路径：
> 1.  `users=1000`, `wait_time=0.95s`（人均 1 RPS）
> 2.  `users=100`, `wait_time=0.05s`（人均 10 RPS，但需确保机器扛得住）
> 具体选哪种，取决于你要测试的是**高并发连接数**（路径1）还是**高吞吐量**（路径2）。

---

### 5. 分布式环境下的叠加效应

在 Master-Worker 模式下，总并发用户数是各 Worker 的**总和**。

\[
\text{集群总 RPS} = \frac{\text{Worker数} \times \text{每Worker用户数}}{\text{RT} + \text{wait\_time}}
\]

- **扩容 Worker**：相当于增加分子（总 `users`），RPS 线性增长。
- **保持 `wait_time`**：确保每个 Worker 内单个用户的频率一致。

**关键计算示例**：
- 目标：全局 RPS = 5000
- 接口 RT = 100ms，设定 `wait_time = constant(0.1)`，则单用户 RPS = `1 / 0.2 = 5`
- 需要的总用户数：`5000 / 5 = 1000` 个
- 若有 5 台 Worker 机器，每台只需分配 `200` 个用户。

---

### 6. 容量规划中的“黄金三角”决策模型

在实际压测中，调整参数遵循以下优先级：

1.  **先定业务模型**：确定单用户的操作频率（即 `wait_time`）。例如，真人浏览设为 `between(3,8)`，高频 API 设为 `constant(0.1)`。
2.  **计算目标 RPS**：根据业务目标（如双十一峰值 10万 RPS），反推所需总用户数 `users = RPS × (RT + wait_time)`。
3.  **检视资源限制**：检查单机内存是否支持这些 `users`（每个协程约几 MB）。若不足，启动分布式 Worker 分摊。
4.  **动态调节**：在压测运行中，若发现 RPS 未达预期但 CPU/内存充足，**优先缩短 `wait_time`**（提升频率）；若发现系统连接数已达上限，**优先减少 `users`**（降低并发）。

---

### 7. 实战代码：根据 `users` 动态调整单用户节奏（高级）

如果你的压测脚本需要在不同 `-u` 参数下自适应（避免小并发时频率过低），可以这样设计：

```python
from locust import HttpUser, task
import os

class AdaptiveUser(HttpUser):
    def dynamic_wait(self):
        # 读取环境变量或 Runner 中的总用户数
        total_users = self.environment.runner.target_user_count if self.environment.runner else 100
        
        # 目标：总 RPS 维持在 500 左右
        # 单用户 RPS = 500 / total_users
        target_interval = total_users / 500.0  # 等待 + RT 的总间隔
        
        # 减去预估的 RT（假设 50ms），得到 wait_time
        estimated_rt = 0.05
        wait = max(0.1, target_interval - estimated_rt)  # 保底 0.1秒
        return wait

    wait_time = dynamic_wait
```


### 💎 总结

- **协同本质**：`users` 设定**并行规模**，`wait_time` 设定**串行节奏**，二者相乘（除）决定最终 RPS。
- **调优铁律**：**不要试图用增加 `users` 来弥补 `wait_time` 过长导致的 RPS 不足**——这会造成大量空闲协程空转，浪费资源。正确做法是先缩短 `wait_time`，若仍不足再增加 `users`。
- **测试意图决定配置**：
  - 测试**系统最大连接/内存容量**：调大 `users`，`wait_time` 设长（如 30秒）。
  - 测试**系统最大吞吐量（RPS）**：`wait_time` 设短（如 0.1秒），`users` 设适量（视响应时间而定）。
