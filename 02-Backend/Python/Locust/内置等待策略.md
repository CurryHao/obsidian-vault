# 内置等待策略

在 Locust 的 `wait_time` 体系中，`between`、`constant` 和 `constant_pacing` 是三个最核心的内置策略。它们分别对应了**“模拟真人随机性”**、**“固定节奏轮询”** 和 **“稳定业务吞吐量”** 三种截然不同的压测需求。

理解它们在**调度机制**上的数学差异，是精准控制流量模型的关键。

---

### 1. `between(min, max)`：模拟真人不可预测性

-   **机制**：每次任务结束后，在 `min` 和 `max` 秒之间**均匀随机**取一个值进行等待。
-   **调度公式**：`实际任务间隔 = 任务耗时 + random.uniform(min, max)`
-   **核心优势**：引入随机抖动，避免所有用户在同一时刻发起请求（避免“共振”），最接近真实人类浏览网页的行为。
-   **适用场景**：**90% 的 Web/App 压测场景**。如浏览商品、查看详情页、填写表单。

```python
from locust import HttpUser, task, between

class RealUser(HttpUser):
    # 每次等待 1~5 秒，模拟翻看手机/阅读内容
    wait_time = between(1, 5)

    @task
    def browse(self):
        self.client.get("/products")
```
**陷阱**：如果 `max` 远大于 `min`，短时间内（如前 1 分钟）实际分布可能不均匀，需运行足够长时间才会趋近理论均值。

---

### 2. `constant(seconds)`：固定节奏轮询

-   **机制**：每次任务结束后，**固定等待** `seconds` 秒，无任何随机性。
-   **调度公式**：`实际任务间隔 = 任务耗时 + seconds`
-   **核心优势**：节奏绝对稳定，便于计算理论最大 RPS，适合模拟定时任务。
-   **适用场景**：模拟后台守护进程、定时健康检查（Heartbeat）、消息队列消费者（拉取模式）。

```python
from locust import HttpUser, task, constant

class HealthCheckUser(HttpUser):
    # 无论上一个请求耗时多久，都固定等 0.5 秒再发下一个
    wait_time = constant(0.5)

    @task
    def ping(self):
        self.client.get("/health")
```

> **致命陷阱**：**极易引发“共振”**。如果 1000 个用户同时启动，且任务耗时稳定，它们会在完全相同的时间点集体发起请求，形成“波峰-波谷”的锯齿形流量，而非平滑压力。**建议慎用**，除非你明确需要这种同步冲击。

---

### 3. `constant_pacing(seconds)`：恒定业务触发频率（最强大）

-   **机制**：保证**两次任务“开始执行”的时间间隔**至少为 `seconds` 秒。它会根据上一次任务的耗时**动态补偿**等待时间。
-   **核心逻辑（重点）**：
    -   若 **任务耗时 < `seconds`**：等待 `seconds - 任务耗时` 秒。（把空闲补足）
    -   若 **任务耗时 >= `seconds`**：**不等待**，立即触发下一个任务。（防止任务堆积导致间隔失控）
-   **调度公式**：`下一次开始间隔 = max(任务耗时, seconds)`

-   **适用场景**：**模拟后台 Job 或业务触发器**。例如“每分钟必须尝试处理 10 笔订单”，如果某笔订单处理慢了，下一笔就立刻执行，尽量保证单位时间内的触发次数恒定。

```python
from locust import HttpUser, task, constant_pacing

class OrderProcessor(HttpUser):
    # 保证每秒最多发起 2 个任务（开始间隔不低于 0.5 秒）
    wait_time = constant_pacing(0.5)

    @task
    def process(self):
        # 假设此接口偶尔耗时 0.8 秒（ > 0.5 ）
        # 下一次会立即执行，不等待，以追赶进度
        self.client.post("/order/process")
```

#### `between` vs `constant_pacing` 深度对比（关键决策点）

| 维度 | **`between`** | **`constant_pacing`** |
| :--- | :--- | :--- |
| **控制的变量** | **空闲间隔**（休息多久） | **触发频率**（多久发起一次） |
| **任务耗时影响** | 总间隔随任务耗时线性增加（拖慢节奏） | 总间隔**不受**任务耗时影响（耗时越长，等待越短） |
| **流量表现** | 压力随接口响应变慢**下降**（越慢越不压） | 压力在接口变慢时**维持恒定**（越慢越死磕） |
| **典型场景** | 真人浏览（响应快了就多刷，慢了就多等） | 自动化守护进程（不管多慢，必须达到每秒 N 次调用） |

---

### 4. 进阶补充：`constant_throughput(rate)` —— 精确限速器

虽然严格意义上它不直接属于“等待策略”的基础类，但它是在 `constant_pacing` 基础上的吞吐量封装。

-   **机制**：通过动态计算期望的请求间隔，确保单个用户每秒执行的任务数趋近于 `rate`。
-   **代码**：`wait_time = constant_throughput(2)` 表示该用户每秒最多执行 2 个任务（即间隔 >= 0.5 秒）。
-   **适用场景**：**严格限流测试**。当你需要确保压测工具本身不会因请求过快触发客户端 429 限流时，用此策略将单用户 RPS 钉死在某个值。

```python
from locust import constant_throughput

class LimitedUser(HttpUser):
    # 该用户全局 QPS 上限为 10 req/s（即间隔不低于 100ms）
    wait_time = constant_throughput(10)
```

### 5. 作用域与继承规则

这三种策略都支持在 **`HttpUser`** 和 **`TaskSet`** 中定义。

-   **顶级定义**：作用于该类下所有未重写的任务。
-   **子级重写**：当进入 `SequentialTaskSet` 时，可重写 `wait_time`，仅作用于该模块内部，退出后恢复父级策略。

```python
class FastModule(TaskSet):
    # 进入此模块后，节奏加快至 0.2 秒固定等待
    wait_time = constant(0.2)

    @task
    def fast_call(self): ...

class MainUser(HttpUser):
    wait_time = between(2, 5)  # 外部慢节奏
    tasks = [FastModule]
```

### 6. 选型速查表

| 需求描述 | 推荐策略 | 理由 |
| :--- | :--- | :--- |
| “模拟用户随机浏览网页” | **`between`** | 随机间隔最符合人类行为，平滑压力。 |
| “每秒固定拉取一次状态” | **`constant(1)`** | 节奏绝对固定，易于计算。 |
| “无论接口多慢，必须保证每分钟触发 60 次” | **`constant_pacing(1)`** | 自动补偿任务耗时，避免频率下降。 |
| “模拟高并发爬虫，持续请求” | **`constant(0)`** 或 **`constant_throughput(100)`** | 前者不加限制（榨干机器），后者精确限速。 |
| “秒杀场景，瞬间爆发但避免工具端超时” | **`constant_pacing(0.01)`** | 保证极高触发频率（100req/s），同时根据响应自动调整。 |

---

### 💎 最终建议

-   **拿不准时，默认用 `between`**，它最安全且最贴近真实用户。
-   只有当你的业务逻辑是**“定时器触发”**或**“后台任务调度”**时，再考虑 `constant_pacing`。
-   **绝对避免**在所有用户上使用 `constant(0)`（零等待），除非你想在压测第一秒就干掉自己的服务器和 Locust 主进程（极易导致端口耗尽或内存溢出）。
