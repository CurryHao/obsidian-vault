# 异常请求明细查看与快速定位

在 Locust 的 Web UI 中，**Failures（失败明细）** 是定位脚本逻辑错误和系统业务异常的“第一现场”。它不同于底层的 **Exceptions（异常堆栈）**，Failures 更偏向于**业务层面的失败记录**（如 HTTP 400/500，或你手动标记的业务错误）。

要快速定位问题，不仅要会看，更要**学会在失败信息中“带料”**。

---

### 1. 在哪里查看 Failures？

- **Web UI 界面**：点击顶部导航栏的 **`Failures`** 选项卡。此处按 `Name`（请求名称）和 `Error`（错误类型）分组聚合，显示发生次数和最后发生时间。
- **CSV 报告**：若启动了 `--csv` 参数，会生成 `[prefix]_failures.csv` 文件，包含所有失败的明细，适合离线分析。
- **控制台日志**：配合 `--loglevel INFO` 或 `--loglevel DEBUG`，失败信息会实时打印在终端。

---

### 2. 关键操作：如何在失败信息中嵌入“定位线索”（核心）

**痛点**：默认的 Failures 只有 `Status Code` 或 `Exception Type`，无法区分是哪个用户、传了什么参数导致失败。

**解法**：在 `catch_response` 的 `failure()` 方法中，**强制携带上下文信息**。

```python
from locust import HttpUser, task

class OrderUser(HttpUser):
    @task
    def create_order(self):
        # 假设每个用户有独立的 user_id 和 product_id
        payload = {"uid": self.user_id, "pid": 1001}
        
        with self.client.post("/order", json=payload, catch_response=True) as resp:
            if resp.status_code != 200:
                # ✅ 优良实践：将关键入参和响应体截断放入失败信息
                resp.failure(
                    f"下单失败 | 状态码: {resp.status_code} | "
                    f"入参: {payload} | "
                    f"响应: {resp.text[:200]}"
                )
            elif resp.json().get("code") != 0:
                # 业务失败同样携带上下文
                resp.failure(
                    f"业务拒绝 | code: {resp.json().get('code')} | "
                    f"msg: {resp.json().get('msg')} | "
                    f"用户: {self.user_id}"
                )
            else:
                resp.success()
```
**效果**：当你在 Web UI 点击 Failures 详情时，直接看到入参和响应片段，无需再去翻日志。

### 3. 快速定位三步法（Case 实战）

假设压测过程中 Failures 突然飙升，请按以下流程操作：

#### Step 1：看类型（区分“网络层”与“业务层”）
- **`ConnectionError` / `Timeout`**：说明压测机到目标服务器网络不通，或服务器连接池已满。
- **`HTTP 500`**：服务器内部错误，需查看服务端日志。
- **自定义业务错误（如 "库存不足"）**：说明业务逻辑触发了限制，系统仍在正常处理。

#### Step 2：看趋势（利用 Charts 辅助）
切回 **Charts** 图表，观察 Failures 曲线是**“瞬时毛刺”**还是**“持续攀升”**。
- **瞬时毛刺**：可能是网络波动或服务器 GC（垃圾回收）停顿，检查是否有定时任务。
- **持续攀升**：说明系统已达瓶颈，需立即关注响应时间（RT）曲线是否同步上升。

#### Step 3：单点复现（使用 `run_single_user`）
如果 Web UI 显示的错误信息不够明确，将失败的入参提取出来，使用 Locust 的调试工具本地复现：

```python
# debug.py (本地运行)
from locust import run_single_user
from my_locustfile import OrderUser

# 仅运行单个用户，并启用调试日志
run_single_user(OrderUser)
```

### 4. 分布式场景下的特殊注意事项

在 Master-Worker 模式下，Failures 由各 Worker 上报，Master 聚合展示。

- **上下文丢失**：如果 Worker 上报的数据过大，可能会截断。确保你的 `failure()` 消息**精简但精准**（如上文案例，控制响应体长度）。
- **定位异常节点**：若怀疑某个 Worker 异常，可在失败消息中加入 `worker_id`：

```python
import os
worker_id = os.environ.get('LOCUST_WORKER_ID', 'unknown')

# 在 failure 消息中携带
resp.failure(f"Worker {worker_id} | 错误信息...")
```

---

### 5. 避免“假成功”陷阱（补充）

很多初学者只看 Failures 为 0 就认定系统健康，这是一个巨大的误区。

- **HTTP 200 掩盖业务失败**：如果未使用 `catch_response` 校验 `code`，即使返回 `{"code": 1001, "msg": "库存不足"}`，Locust 也会统计为成功（Success）。
- **解决方案**：强制为所有**核心业务接口**（如下单、支付）启用 `catch_response` 并进行业务断言。

---

### 6. 快速诊断速查表

| Failures 显示内容 | 大概率原因 | 优先排查方向 |
| :--- | :--- | :--- |
| `ConnectionError: 111` | 目标端口未开放或连接被拒绝 | 检查服务是否存活，防火墙/安全组规则 |
| `ReadTimeout` / `Timeout` | 服务器响应过慢 | 检查服务端 CPU/DB 连接数，是否有死锁 |
| `HTTP 429 Too Many Requests` | 触发了限流（Rate Limit） | 降低并发数，或检查是否未携带必要 Token |
| `HTTP 404` | URL 路径错误 | 检查 `self.client.get()` 中的路径，是否遗漏 `name` 参数 |
| `JSONDecodeError` | 响应非 JSON（可能是 HTML 错误页） | 打印响应体内容，确认服务器是否返回了异常堆栈 |
| 自定义业务错误 | 业务逻辑拦截（如余额不足） | 检查前置数据准备（账号是否具备资格） |

### 💎 总结
- **定位核心**：不要在 Failures 里只留状态码，**把入参和响应片段塞进去**，实现“看图说话”。
- **观察维度**：区分“网络故障”和“业务拒绝”，前者查机器，后者查脚本数据。
- **分布式排查**：给 Worker 打上 ID 标签，避免日志混乱。
