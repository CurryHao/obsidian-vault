# 固定步长与吞吐量精准限制

`constant_pacing` 是 Locust 中最被低估但最具实战价值的等待策略。它不是为了模拟“用户思考”，而是为了**精准控制业务触发频率**，防止在服务变慢时压测工具自身引发“雪崩式”重试。

如果你想让压测工具像一个**稳健的后台消费者**（无论上游多慢，都严格控制每秒发起的任务数），`constant_pacing` 就是你的不二之选。

---

### 1. 核心机制：控制“开始时间”而非“结束时间”

这是理解 `constant_pacing` 的**第一性原理**。它的调度逻辑如下：

```text
假设 constant_pacing(5)  # 保证两次任务开始间隔 >= 5 秒

场景 A（接口很快）： 任务耗时 0.5 秒 -> 等待 4.5 秒 -> 启动下一次
场景 B（接口很慢）： 任务耗时 6.0 秒 -> 等待 0 秒   -> 立即启动下一次（因为已经超了）
```
**关键公式**：
`实际等待时间 = max(0, pacing - 上一次任务耗时)`

-   **核心差异**：`between` 控制的是**休息多久**；`constant_pacing` 控制的是**多久干一次活**。它把任务耗时“吃掉”了一部分等待时间。

---

### 2. 如何实现“吞吐量精准限制”？

`constant_pacing(seconds)` 直接限制了**单个用户**的最大任务启动频率。

-   **单用户理论最大 RPS（吞吐量）**：`1 / seconds`
-   **集群总吞吐量上限**：`并发用户数 / seconds`（前提是任务耗时 < seconds）

**代码实战：精准限流到 2 RPS**
假设你有一个敏感的下单接口，希望**全局无论有多少用户，绝对不能超过 2 RPS**。

```python
from locust import HttpUser, task, constant_pacing

class SafeOrderUser(HttpUser):
    # 设置步长为 0.5 秒，意味着该用户最多每秒发起 2 个任务
    # 若部署 1 个这种用户，全局 RPS 封顶即为 2
    wait_time = constant_pacing(0.5)

    @task
    def create_order(self):
        # 假设此接口内部逻辑复杂，偶尔耗时 1.2 秒
        # 此时由于 1.2 > 0.5，下一次会立即执行，以补偿落后的进度
        self.client.post("/order", json={"product": "book"})
```

> **注意**：如果任务耗时长期大于 `pacing` 值，该用户会进入 **“无等待”** 模式（立即执行下一次）。此时虽无法精准限制 RPS，但能确保**工具端不会积压任务**，这比 `between` 导致的任务堆积要安全得多。

---

### 3. 进阶对比：`constant_pacing` vs `constant_throughput`

这两个函数看起来都能控制吞吐量，但机制截然不同，面对**服务变慢**时的表现天差地别：

| 维度 | **`constant_pacing(0.5)`** | **`constant_throughput(2)`** |
| :--- | :--- | :--- |
| **控制逻辑** | 控制**启动间隔**（绝对硬限制） | 控制**每秒执行次数**（统计学调节） |
| **服务变慢时** | **不再等待**，立即发起下一次（用户不闲着，但频率不会超过物理极限） | **缩短等待时间**以强行达到 2 RPS，可能产生比预期更高的并发度 |
| **最大并发风险** | 低。仅维持 1 个请求在网络中飞行 | **高**。若接口耗时 5 秒，为了达到 2 RPS，工具会同时发出 10 个请求（窗口重叠） |
| **适用场景** | **后台任务消费者**、队列处理、严格限流保护 | 强调**统计目标**的基准测试（不考虑变慢情况） |

**实战选择**：如果你的目标是**“保护下游系统不被冲垮”**，请用 `constant_pacing`。`constant_throughput` 可能会在系统慢的时候反而增加并发压力，导致恶性循环。

---

### 4. 分布式环境下的吞吐量计算陷阱

在 Master-Worker 模式下，`wait_time` 作用于**每个 Worker 的每个协程**。因此，**总吞吐量是线性叠加的**。

**计算公式**：
`集群总 RPS = 总并发用户数 × (1 / pacing)`

**示例**：
-   配置：`constant_pacing(0.5)`（单用户 2 RPS）
-   启动：`-u 1000`（1000 个用户） 且 接口耗时 < 0.5s
-   预期总 RPS ≈ `1000 × 2 = 2000 RPS`

> **警告**：如果接口耗时 > pacing，则上述公式失效，实际 RPS 会趋近于 `总并发数 / 接口耗时`（因为无等待）。所以在设计压测时，**请确保接口耗时远小于 pacing 值**，才能实现精准限流。

---

### 5. 超时与死锁风险（关键避坑）

如果接口耗时**偶尔超过 pacing 值**，`constant_pacing` 会立即发起下一次。但如果接口耗时**长期超过客户端设置的 `timeout` 并抛出异常**呢？

-   异常抛出后，`wait_time` 依然会被调用。
-   由于任务耗时超长（比如 30 秒），`pacing` 设为 1 秒，则下一次 **立即执行**。
-   这可能导致用户疯狂重试一个已超时的接口，**占用大量 CPU 和端口资源**。

**解决方案**：结合 `catch_response` 和 `StopUser`，在遇到连续超时时主动退出，避免僵尸协程。

```python
class SmartUser(HttpUser):
    wait_time = constant_pacing(1)
    consecutive_failures = 0

    @task
    def critical_api(self):
        try:
            self.client.post("/critical", timeout=5)
            self.consecutive_failures = 0  # 成功则重置
        except Exception:
            self.consecutive_failures += 1
            if self.consecutive_failures >= 3:
                # 连续失败3次，说明下游极慢，主动退出用户释放资源
                raise StopUser()
```

### 6. 实战选型决策树

| 业务场景描述 | 推荐策略 | 理由 |
| :--- | :--- | :--- |
| **模拟网页真人浏览** | `between` | 随机性符合人类直觉，压力平滑。 |
| **模拟守护进程轮询**（如读取配置） | `constant` | 节奏绝对固定，便于日志分析。 |
| **模拟消息队列消费者**（每 100ms 拉取一次） | **`constant_pacing(0.1)`** | 即使处理慢了，也不堆积，保证消费进度。 |
| **对下游限流保护**（绝对不能超过 100 RPS） | **`constant_pacing(0.01)`** 限制单用户 + 控制总 `-u` | 硬性限制最大并发请求数。 |
| **模拟秒杀高频刷接口** | `constant_throughput` 或极短 `constant_pacing(0.001)` | 追求极限吞吐，但需配合超时断连。 |

---

### 💎 总结

-   **`constant_pacing` 的本质是“任务启动间隔控制器”**，它的设计初衷是**保护系统**，防止压测工具在服务变慢时变本加厉地施压。
-   如果你想做**严格的 QPS 准入测试（SLA 验证）**，`constant_pacing` 是最佳搭档。配合 `-u` 参数，你可以轻松推算出集群的理论最大 RPS。
-   **永远记住**：当任务耗时接近或超过 `pacing` 值时，`constant_pacing` 会退化为 `constant(0)`（零等待），此时你必须通过 `timeout` 和异常处理来兜底。

如果你正在设计一个**“消息队列生产者”**或**“全链路压测流量注入器”**，`constant_pacing` 能帮你把注入速率钉得死死的。如果你想进一步了解**如何结合 `LoadTestShape` 动态调整 `pacing` 值**（例如压力越大，步长越长，模拟限流反馈），可以告诉我，我们继续深入。
