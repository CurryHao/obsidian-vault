# 工作节点注册与注销事件处理

在 Locust 的 Master-Worker 分布式架构中，**Worker 注册与注销**是集群协调的基石。理解并利用这两个生命周期事件，可以实现**动态数据分发**、**集群健康监控**以及**资源预加载**。

Locust 提供了专门的内部事件钩子来处理这些行为，但需要明确：**这些事件主要在 Master 端触发**，用于感知 Worker 的状态变化。

---

### 1. 核心事件钩子（Master 端监听）

| 事件 | 触发时机 | 典型用途 |
| :--- | :--- | :--- |
| **`worker_connect`** | Worker 成功连接到 Master 并完成握手时触发。 | **初始化分配**：为刚上线的 Worker 分配唯一的测试数据段（如用户 ID 区间）。 |
| **`worker_ready`** | Worker 加载完 `User` 类，真正准备好执行任务时触发（在 `worker_connect` 之后）。 | **确认就绪**：标记该节点可以接收压测任务，用于 `--expect-workers` 的等待逻辑。 |
| **`worker_disconnect`** | **（需注意）** 官方事件中**没有**直接的 `worker_disconnect` 事件。Worker 掉线由 Master 的**心跳超时**（`--master-heartbeat-timeout`）机制自动处理，超时后 Master 会将其移出活跃列表。 | **兜底清理**：如需感知掉线，需通过 `@events.heartbeat` 自行轮询检查状态。 |

> **作用域说明**：`worker_connect` 和 `worker_ready` 仅在 **Master 节点**触发，Worker 自身不会触发这些事件。

---

### 2. 实战场景一：Worker 注册时动态分配测试数据（数据池分片）

在分布式压测中，若 10 个 Worker 同时使用同一个账号池，会产生严重的并发冲突（Token 互踢）。最佳实践是在 Worker **注册时**，由 Master 为其分配专属的数据分片。

```python
# master_listener.py
from locust import events
from locust.runners import MasterRunner

# Master 端维护的数据分配器
class WorkerDataAllocator:
    def __init__(self):
        self.worker_id_map = {}  # 记录 client_id -> 分配的数据段
        self.next_id = 0
        self.total_users = 10000  # 假设有 1 万个测试账号

    def allocate_segment(self, client_id):
        # 每个 Worker 分配 1000 个账号
        start = self.next_id
        end = start + 1000
        if end > self.total_users:
            end = self.total_users
        self.worker_id_map[client_id] = (start, end)
        self.next_id = end
        return start, end

allocator = WorkerDataAllocator()

@events.worker_connect.add_listener
def on_worker_connect(environment, client_id, **kwargs):
    """当 Worker 首次连接时，为其分配数据区间"""
    if isinstance(environment.runner, MasterRunner):
        start, end = allocator.allocate_segment(client_id)
        print(f"[Master] Worker {client_id[:8]} 已注册，分配账号区间: {start}-{end}")
        
        # 注意：这里只是在 Master 内存中记录了分配，还需要将数据传递给 Worker
        # 传递方式见下文“事件联动”部分
```
**如何将分配的数据传给 Worker？**  
在 `worker_connect` 中无法直接向 Worker 发消息，需通过 **`@events.worker_report`**（Worker 主动上报时）或 **Worker 启动时主动请求**。更简单的做法是：在 Worker 的 `test_start` 中向 Master 请求数据，或者利用共享存储（如 Redis）让 Worker 自行取用。

### 3. 实战场景二：监控集群健康与动态扩缩容

通过监听注册事件，你可以实时获取集群中活跃 Worker 的数量，结合 `--expect-workers` 可以实现“等待所有 Worker 就绪再开始”的能力。

```python
from locust import events

@events.worker_ready.add_listener
def on_worker_ready(environment, client_id, **kwargs):
    """Worker 完全就绪时触发"""
    if isinstance(environment.runner, MasterRunner):
        active_workers = len(environment.runner.clients)  # 所有已连接的 Worker ID 列表
        print(f"[Master] Worker {client_id[:8]} 就绪，当前活跃: {active_workers}")
        
        # 可选：如果达到预期数量，可以自动触发开始？
        # expected = environment.parsed_options.expect_workers
        # if active_workers >= expected:
        #     environment.runner.start()
```

### 4. 处理 Worker 注销（掉线感知）

由于官方没有 `worker_disconnect` 事件，若需要感知 Worker 掉线（例如缩容或宕机），可以通过 **`@events.heartbeat`** 在 Master 端做轮询检查。

```python
import time
from locust import events
from locust.runners import MasterRunner

last_seen = {}

@events.heartbeat.add_listener
def on_heartbeat(environment, **kwargs):
    """Master 端每 3 秒（默认）触发一次心跳事件"""
    if not isinstance(environment.runner, MasterRunner):
        return
    
    current_workers = set(environment.runner.clients.keys())
    
    # 检测掉线（假设 15 秒未出现即为掉线）
    now = time.time()
    for cid in current_workers:
        last_seen[cid] = now
    
    offline = [cid for cid, t in last_seen.items() if now - t > 15 and cid not in current_workers]
    for cid in offline:
        print(f"⚠️ Worker {cid[:8]} 已掉线！")
        # 可以在此触发告警或重新分配数据
        del last_seen[cid]
```

> **更优雅的方式**：直接利用 `environment.runner` 的内置状态。MasterRunner 内部维护了 `worker_state`，但直接读取 `clients` 字典是最可靠的。

### 5. 事件联动：结合 `test_start` 执行集群检查

通常在 `test_start` 阶段，我们可以检查注册的 Worker 数量是否达到预期，未达标则主动退出。

```python
@events.test_start.add_listener
def on_test_start(environment, **kwargs):
    if isinstance(environment.runner, MasterRunner):
        expected = environment.parsed_options.expect_workers or 0
        actual = len(environment.runner.clients)
        if expected > 0 and actual < expected:
            print(f"❌ 预期 {expected} 个 Worker，实际只有 {actual} 个，取消压测！")
            environment.runner.quit()  # 终止测试
```

---

### 6. 关键差异：Worker 侧如何“注册”？

以上所有事件都在 Master 端处理。如果你需要在 Worker 侧知道“我已成功注册”，Worker 本身无法直接捕获 `worker_connect`（因为这是 Master 收到的消息）。Worker 可以在 `on_start` 或自定义初始化逻辑中通过发送自定义消息来确认，但通常没有必要——Worker 只要连接成功，控制台就会打印 `Connected to master`。

---

### 7. 核心避坑指南

| 陷阱 | 现象 | 解决方案 |
| :--- | :--- | :--- |
| **在 `worker_connect` 中尝试直接发消息给 Worker** | 无直接 API 支持，数据无法传递。 | 使用共享 Redis 或让 Worker 在 `test_start` 中主动拉取配置。 |
| **`worker_ready` 和 `worker_connect` 顺序混淆** | `worker_ready` 在 `worker_connect` 之后触发，务必区分“已连接”和“已准备”。 | 数据分配放 `connect`，资源预热放 `ready`。 |
| **依赖心跳检测“掉线”但心跳间隔未调整** | 默认 3 秒一次，网络抖动可能误报。 | 调整 `--heartbeat-interval` 和 `--master-heartbeat-timeout` 参数。 |
| **分布式下 `environment.runner.clients` 在 Worker 端为空** | Worker 节点上该字典是空的，导致代码报错。 | 监听器开头始终检查 `isinstance(environment.runner, MasterRunner)`。 |

---

### 💎 总结与最佳实践

- **注册（Register）**：使用 `@events.worker_connect` 和 `@events.worker_ready` 在 Master 端处理 Worker 上线逻辑（日志、计数、预热）。
- **注销（Unregister/Offline）**：无原生事件，通过 **心跳超时机制** + **轮询 `clients` 字典** 自行实现。
- **数据协调**：不要在注册事件中做跨节点网络通信（如直接 RPC）。**推荐做法**：Worker 通过 `report_to_master` 主动上报需求，或依赖外部存储（Redis/DB）实现数据分片感知。
- **运维联动**：如果你在 Kubernetes 中运行，Worker 的注册事件可以配合 Hook 实现动态 DNS 更新或优雅停机延迟（`preStop`）。

若你想深入 **Worker 向 Master 主动上报自定义数据**（如本机 CPU 负载），并利用注册事件建立反向控制通道，可以告诉我，我们继续扩展自定义消息传递方案。
