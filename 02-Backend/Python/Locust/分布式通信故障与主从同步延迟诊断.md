# 分布式通信故障与主从同步延迟诊断

## Locust 分布式通信故障与主从同步延迟诊断指南

在分布式压测中，Master 和 Worker 之间的通信是核心生命线。任何通信故障或同步延迟都可能导致测试结果不准确、负载不均衡、甚至测试中断。本章系统化梳理常见故障模式、诊断工具和优化策略。

---

### 一、分布式通信架构回顾

| 组件 | 端口 | 协议 | 作用 |
|------|------|------|------|
| **Master** | 5557 | TCP | Worker 注册、任务调度、统计收集 |
| **Master** | 5558 | TCP | Worker 心跳检测（2.x 中合并到 5557） |
| **Worker** | 动态端口 | TCP | 连接 Master、执行任务、发送统计 |

通信流程：
1. Worker 启动后通过 `--master-host` 连接 Master 的 5557 端口。
2. Master 通过心跳（默认 1 秒）检测 Worker 存活。
3. 每个 Worker 定期将本地统计数据（`stats` 和 `exceptions`）发送给 Master。
4. Master 汇总所有 Worker 数据并暴露在 Web UI / API。

---

### 二、常见通信故障分类

| 故障现象 | 可能原因 | 影响 |
|---------|---------|------|
| **Worker 连接不上 Master** | 网络不通、防火墙、Master 未启动、端口错误 | 测试无法启动 |
| **Worker 频繁断连** | 网络丢包、负载过高、心跳超时 | 统计数据缺失，RPS 波动 |
| **Master 无法收到 Worker 统计** | Worker 进程挂起、统计队列溢出 | 报告不完整 |
| **主从同步延迟** | 网络延迟、Worker 负载高、Master 处理瓶颈 | 实时 UI 滞后，控制指令延迟 |
| **Worker 注册失败** | Worker 版本不匹配、Master 重启 | Worker 被拒绝 |

---

### 三、诊断工具与命令

#### 3.1 网络连通性检查

```bash
# 从 Worker 节点测试到 Master 的端口连通性
telnet <master_host> 5557
nc -zv <master_host> 5557
```
## 3.2 查看连接状态

```bash
# 在 Master 节点查看已连接的 Worker
ss -tulnp | grep 5557
netstat -antp | grep 5557
lsof -i :5557

# 查看每个连接的活跃状态
ss -o state established '( dport = :5557 )'     # 从 Worker 角度
```

#### 3.3 查看 Locust 日志

启用 `-L DEBUG` 可看到详细的通信日志：

```bash
locust -f locustfile.py --master -L DEBUG
locust -f locustfile.py --worker --master-host <ip> -L DEBUG
```

关键日志：
- `[Worker] Registered with master` → Worker 成功注册。
- `[Worker] Heartbeat timeout` → 心跳超时。
- `[Master] Worker <id> disconnected` → Worker 断开。
- `[Master] Worker <id> stats received` → 统计接收成功。

#### 3.4 监控系统资源

```bash
# 在 Master 上查看 CPU/内存
top -p <master_pid>

# 查看网络流量
iftop -i eth0

# 查看 socket 缓冲区大小
cat /proc/sys/net/core/rmem_max
cat /proc/sys/net/core/wmem_max
```

#### 3.5 抓包分析

若怀疑网络层问题，可用 `tcpdump` 捕获通信包：

```bash
tcpdump -i eth0 port 5557 -w master_worker.pcap
```

用 Wireshark 分析重传、丢包和 RST 标志。

### 四、同步延迟诊断

#### 4.1 延迟现象

- Web UI 上的 RPS 曲线滞后于实际请求 5-10 秒。
- 停止压测后，UI 上的统计数据仍在更新（残留统计）。
- `--csv` 导出的历史数据时间戳不准确。

#### 4.2 原因分析

| 原因 | 说明 |
|------|------|
| **Worker 统计上报间隔** | Worker 默认每 2 秒上报一次，可通过 `--stats-history-interval` 调整 |
| **网络延迟** | 高 RTT 导致统计包传输慢 |
| **Master 处理瓶颈** | 当 Worker 数过多（>100）或高 RPS 时，Master 的统计聚合可能成为瓶颈 |
| **Worker 自身负载高** | 高 CPU 占用导致统计收集和上报被延迟 |
| **队列积压** | Worker 内部统计队列（`stats`）积压，导致上报滞后 |

#### 4.3 诊断方法

1. **查看 Master 处理延迟**：
   - 在 Master 日志中搜索 `Received stats from worker`，对比接收时间与 Worker 发送时间（可在 Worker 日志中查看发送时间）。
2. **检查 Worker 的统计队列长度**：
   - Locust 2.x 中，可通过 Worker 的 `environment.runner.stats` 对象获取未上报的请求数（需自定义代码输出）。
3. **使用系统时间同步**：
   - 确保所有节点的 NTP 时间同步，避免时间戳偏差。

### 五、解决方案与优化

#### 5.1 通信故障修复

| 问题 | 修复方法 |
|------|---------|
| **端口被防火墙阻止** | 开放 Master 的 5557/5558 端口；在云安全组中添加规则。 |
| **Master 未启动** | 确认 Master 进程正在运行；检查 `--master-bind-host` 是否绑定到正确 IP。 |
| **Worker 使用错误地址** | Worker 的 `--master-host` 必须指向 Master 可达的 IP（不要用 `127.0.0.1`）。 |
| **版本不匹配** | 确保 Master 和所有 Worker 使用相同版本的 Locust。 |
| **Worker 资源耗尽** | 增加 Worker 机器的 CPU/内存，或减少单 Worker 的并发用户数。 |

#### 5.2 同步延迟调优

| 调整项 | 建议值 | 说明 |
|-------|--------|------|
| `--stats-history-interval` | 3-5 秒 | 增加上报间隔，减少 Master 负载 |
| `--worker-processes` | 根据 CPU 核数 | 单机多 Worker 时，Master 会汇总多个 Worker 统计 |
| `--master-bind-host` | 指定内网 IP | 避免使用 `0.0.0.0` 导致非预期绑定 |
| `net.core.wmem_max` / `rmem_max` | 增大到 16MB | 提高 socket 缓冲区，减少拥塞 |
| Worker 数量 | 不超过 50-100 | 过多 Worker 会增加 Master 聚合负担 |

#### 5.3 高可用与容错

- **Master 重启**：Worker 会自动尝试重连（需确保 Master 重新启动后端口可访问）。
- **Worker 自动恢复**：Locust Worker 默认会持续重试连接，无需手动重启。
- **使用消息队列缓冲**：若需更高可靠性，可考虑使用 Kafka 等中间件作为统计传输层（需自定义）。

### 六、实战案例

**场景**：100 个 Worker，每个 Worker 100 并发用户，总并发 10000。测试初期正常，30 分钟后出现大量 `Heartbeat timeout`，且 Web UI 刷新缓慢。

**诊断**：
1. Master 节点 CPU 达到 100%（单核），内存使用正常。
2. 查看 Master 日志，发现大量 `Received stats from worker` 消息，每条消息处理耗时超过 10ms。
3. 网络延迟正常（<1ms）。
4. 发现 Worker 的统计上报频率为默认 2 秒，导致 Master 每秒需处理 50 个统计包（100 个 Worker * 2 秒/包 = 50 包/秒），加上高 RPS 的聚合计算，CPU 打满。

**解决方案**：
- 将 `--stats-history-interval` 调整为 5 秒，减少上报频率。
- 将 100 个 Worker 合并为 30 个，每 Worker 增加并发用户数（从 100 提高到 333）。
- 升级 Master 机器为 4 核 CPU。

优化后，Master CPU 降至 60%，Web UI 响应恢复正常。

---

### 七、监控与告警

建议在压测过程中监控以下指标，提前预警：

| 指标 | 采集方式 | 告警阈值 |
|------|---------|---------|
| Master CPU 使用率 | `top` / `node_exporter` | > 80% |
| Worker 心跳超时次数 | Locust 日志 / 自定义计数 | 连续 3 次超时 |
| 统计上报延迟 | Worker 发送时间 vs Master 接收时间 | 延迟 > 5 秒 |
| 网络重传率 | `netstat -s | grep retrans` | > 1% |
| 活动 Worker 数量 | `kubectl get pods` 或 Master API | 与期望值不符 |

---

### 总结

分布式通信是 Locust 压测的基石，问题往往源于网络配置、资源瓶颈或参数设置不当。遵循“先连通性、再性能、最后调优”的排查顺序，结合日志、系统监控和网络工具，可以快速定位并解决绝大多数故障。对于大规模部署（> 50 Worker），建议在测试前进行小规模预演，验证通信稳定性，并根据预演结果调整上报间隔和资源配额。
