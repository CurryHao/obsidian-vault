# Worker数量与目标系统负载能力的平衡计算

## Worker 数量与目标系统负载能力的平衡计算

在 Locust 分布式压测中，**Worker 数量的设定**直接决定了你能施加的负载上限。  
如果 Worker 太少，可能无法压出目标系统的瓶颈；  
如果 Worker 太多，不仅浪费资源，还可能因压测机自身成为瓶颈（如网络带宽、CPU 过载）而导致测试结果失真。  

因此，我们需要一套科学的计算方法来平衡两者。

---

### 一、关键变量定义

| 变量 | 含义 | 单位 |
|------|------|------|
| **目标 RPS** (`RPS_target`) | 你希望目标系统承受的每秒请求数 | req/s |
| **单 Worker 可支撑的 RPS** (`RPS_worker`) | 在给定硬件与脚本复杂度下，单个 Worker 能稳定产生的最大 RPS | req/s |
| **期望并发用户数** (`Users`) | 用户脚本中设定的并发用户总数 | 用户 |
| **平均响应时间** (`RT_avg`) | 目标系统在测试中的平均响应时间 | 秒 |
| **思考时间** (`Think_time`) | 用户脚本中设定的等待时间 | 秒 |
| **目标系统资源上限**（如 CPU 核心、内存、带宽） | 用于判断何时达到系统瓶颈 | – |
| **压测机资源上限**（CPU、内存、网络带宽） | 防止压测机自身成为瓶颈 | – |

---

### 二、基础计算公式

#### 1. 根据目标 RPS 计算所需 Worker 数
```
Worker 数量 = ceil( RPS_target / RPS_worker )
```

#### 2. 根据并发用户数估算 RPS
当你知道目标并发用户数 (`Users`) 和每个用户的请求频率时，可以估算 RPS：
```
RPS ≈ Users / (RT_avg + Think_time)
```
> 注：这是理论最大 RPS，实际会受网络延迟、系统响应波动等影响。

#### 3. 综合公式
```
Worker 数量 = ceil( Users / (RPS_worker * (RT_avg + Think_time)) )
```
或者直接使用目标 RPS。

---

### 三、如何估算单 Worker 的 RPS 能力 (`RPS_worker`)

这是计算中最关键、最易变化的参数。它取决于：

- **压测机硬件**：CPU 核心数、主频、内存大小、网卡带宽。
- **脚本复杂度**：请求数量、解析 JSON、处理正则表达式、等待时间等。
- **协议类型**：HTTP/1.1（短连接） vs HTTP/2（多路复用） vs WebSocket（长连接），RPS 差别很大。
- **网络延迟**：压测机到目标系统的 RTT（往返时间）越高，单 Worker 能产生的 RPS 越低。
- **Locust 内部开销**：使用 `FastHttpUser` 比 `HttpUser` 性能高 5~10 倍。

#### 获取 `RPS_worker` 的推荐方法：

1. **经验值参考（基于常见云主机）**：
   - 普通 2vCPU 虚拟机 + `HttpUser` + 简单 JSON 响应：约 **500~1000 RPS**。
   - 同配置 + `FastHttpUser`：约 **2000~3000 RPS**。
   - 4vCPU + `FastHttpUser`：可达 **5000+ RPS**（取决于网络）。
   - WebSocket 长连接模式：每个 Worker 通常支持 **1000~3000 并发连接**，RPS 取决于消息频率。

2. **预测试（推荐）**：
   在目标系统未上线或使用 mock 服务器时，先运行一个小规模的单 Worker 压测，逐步增加并发用户，观察该 Worker 的 RPS 曲线，找到其稳定上限（即 RPS 不再随用户增加而增长的点）。此值即为 `RPS_worker`。

3. **考虑安全边际**：保守起见，取预测试值的 **70%~80%** 作为设计值，防止波动导致压测机资源耗尽。

---

### 四、目标系统负载能力的评估

Worker 数量并非无限增长。你需要同时判断目标系统何时达到瓶颈，以便决定是否继续增加 Worker。

**逐步加压法**：
1. 从少量 Worker（如 1 个）开始，记录目标系统的 CPU、内存、网络及 RPS、响应时间。
2. 逐步增加 Worker，观察目标系统资源利用率与响应时间的变化。
3. 当出现以下任一情况时，说明已达到目标系统的负载上限：
   - CPU 利用率持续 > 80%；
   - 响应时间出现非线性增长（如从 100ms 突然跳到 500ms）；
   - 错误率（超时、5xx）显著增加；
   - 吞吐量（RPS）不再随 Worker 增加而增长，甚至下降。

此时的 Worker 数量即为当前环境下的最优数量。

---

### 五、示例计算

**场景**：  
- 目标：需要验证 API 网关在 **5000 RPS** 下的稳定性。
- 环境：使用 4vCPU、8GB 内存的 Worker 节点，网络延迟 <5ms，脚本为 `FastHttpUser` 简单 GET 请求。
- 预测试结果：单 Worker 在 4vCPU 下稳定产生约 **3000 RPS**。

**计算**：
```
Worker 数量 = ceil(5000 / 3000) = 2
```
但考虑到安全边际（20%），实际应使用 3 个 Worker，确保压测机不会成为瓶颈。

**同时验证压测机资源**：
- 3 个 Worker 总计目标 RPS = 9000（但目标系统可能只承受 5000，其余压力会因排队而回落，实际产生 5000）。
- 检查网络：单 Worker 平均响应大小 1KB，则总带宽 = 5000 * 1KB ≈ 5MB/s，远低于 1Gbps 网卡（约 125MB/s），带宽充足。
- 检查 CPU：预计每个 Worker CPU 占用约 60~70%，3 个 Worker 总 CPU 约 180~210%，4vCPU 可承受（每个 vCPU 占 100%，总 400%）。

**结论**：3 个 Worker 是安全且有效的选择。

---

### 六、动态伸缩策略（KEDA / HPA）

在生产环境中，你可能需要根据实时负载动态调整 Worker 数量。常见做法：

- **基于队列长度**（如 Kafka 积压、Redis 列表长度）：当积压增加时自动扩容 Worker。
- **基于目标 RPS 与当前 RPS 的差距**：如果当前 RPS 低于目标值一定比例（如 20%），则增加 Worker。
- **基于压测机自身的 CPU/内存阈值**：当 Worker Pod 的 CPU 超过 70% 时扩容，避免单个 Worker 过载。

使用 KEDA 或 Kubernetes HPA 结合自定义指标，可以实现自动伸缩，确保持续平衡。

---

### 七、最佳实践总结

| 步骤 | 操作 |
|------|------|
| 1 | 明确测试目标（目标 RPS 或并发用户数）。 |
| 2 | 通过预测试或经验估算单 Worker 的 RPS 上限。 |
| 3 | 计算所需 Worker 数量，并增加 20%~30% 安全余量。 |
| 4 | 验证压测机资源（CPU、内存、网络）不会成为瓶颈。 |
| 5 | 采用逐步加压法，观察目标系统的资源变化，找到系统瓶颈点。 |
| 6 | 若目标系统提前达到瓶颈，则停止增加 Worker，记录瓶颈数据。 |
| 7 | 在长期/夜间的回归测试中，考虑使用自动伸缩机制动态调整 Worker。 |

**关键原则**：  
- **Worker 数量应服务于测试目标**，而非越多越好。  
- **始终确保压测机自身资源充足**（CPU < 70%、内存未满、带宽未饱和）。  
- **数据驱动**：每次测试前进行小规模探测，避免因网络波动或系统更新导致估算失效。

通过科学的计算与灵活的伸缩机制，你既能精准施压，又能避免资源浪费，让性能测试真正服务于容量规划与系统优化。
