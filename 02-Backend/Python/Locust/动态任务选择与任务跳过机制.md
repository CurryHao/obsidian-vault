# 动态任务选择与任务跳过机制

在 Locust 中，**动态任务选择**与**任务跳过**是构建智能、自适应压测脚本的高级能力。它们能让你根据**服务器响应、用户状态或外部数据**，在运行时动态决定“接下来做什么”或“是否跳过当前任务”，从而模拟出更真实、更智能的用户行为。

---

### 1. 任务跳过（Task Skipping）：不执行就完事

“跳过”意味着当前用户**依然存活**，只是此次调度循环中**放弃执行**某个特定任务。主要实现方式有：

#### A. 方法内提前 `return`（最轻量）
在 `@task` 方法顶部进行条件判断，若不满足则直接 `return`。调度器会认为该方法已执行完毕，并立即进入下一个任务选择或 `wait_time` 等待。

```python
from locust import HttpUser, task, between
import random

class SmartUser(HttpUser):
    wait_time = between(1, 3)
    user_tier = "normal"  # 假设从 on_start 中获取

    @task(3)
    def browse(self):
        # 所有人都能浏览
        self.client.get("/")

    @task(1)
    def vip_discount(self):
        # 仅 VIP 用户执行，非 VIP 直接跳过
        if self.user_tier != "vip":
            return  # 跳过此任务，不发送任何请求
        self.client.get("/vip/coupon")
```
```code**关键点**：`return` 不会影响统计（既不算成功也不算失败），且用户会继续执行后续调度循环。

#### B. 结合 `catch_response` 标记失败但继续运行
若条件不满足时你希望**计入统计（作为失败）**，但**不终止用户**，可以使用 `catch_response` 并标记失败，随后 `return`。

```python
@task
def limited_stock(self):
    with self.client.get("/stock_check", catch_response=True) as resp:
        if resp.json().get("available") == 0:
            resp.failure("库存为0，本次跳过")
            return  # 用户继续存在，但记录了一次失败
        resp.success()
        # 继续执行后续购买逻辑...
```

#### C. `SequentialTaskSet` 中的条件中断
在顺序流中，若某一步不满足前置条件，使用 `self.interrupt()` 可以**跳过该任务集剩余的步骤**，回到父级任务集。

```python
class CheckoutFlow(SequentialTaskSet):
    @task
    def step1_check_cart(self):
        resp = self.client.get("/cart")
        if not resp.json()["items"]:
            # 购物车为空，跳过整个结账流程
            self.interrupt()  # 回到父级 User，继续执行其他 TaskSet
            return
        print("购物车有商品，继续")

    @task
    def step2_pay(self):
        self.client.post("/pay")
        self.interrupt()  # 正常结束
```

### 2. 动态任务选择（Dynamic Task Selection）

“动态选择”指的是用户在运行时改变接下来要执行的任务，而非死板地遵循初始权重配置。

#### A. 运行时切换 `TaskSet`（执行新模块）
使用 `self.execute(OtherTaskSet)` 在任意时刻强行切入另一个任务集，常用于处理“验证码弹窗”、“跳转至第三方支付”等场景。

```python
class PaymentRedirect(TaskSet):
    @task
    def handle_redirect(self):
        # 模拟被重定向到外部支付
        self.client.get("/external_pay")
        # 处理完支付，返回主流程
        self.interrupt()

class OrderFlow(SequentialTaskSet):
    @task
    def submit_order(self):
        resp = self.client.post("/order")
        if resp.status_code == 302:  # 需要重定向支付
            # 动态跳转至支付处理模块
            self.execute(PaymentRedirect)
        # 支付模块结束后，会回到此处继续执行后续任务（如果有）
        self.interrupt()
```

#### B. 动态修改实例的 `tasks` 属性（运行时改变权重/任务列表）
`User` 实例的 `tasks` 属性（列表或字典）是**可写的**。在 `on_start` 或任务方法中修改它，会影响该用户**后续所有调度循环**的任务池。

```python
class AdaptiveUser(HttpUser):
    tasks = [BrowseTaskSet, SearchTaskSet]  # 初始权重均为1

    def on_start(self):
        # 通过外部 API 获取用户画像
        resp = self.client.get("/user/profile")
        if resp.json().get("is_bot"):
            # 如果是爬虫，强制只执行高频浏览任务
            self.tasks = [BrowseTaskSet]  # 只保留浏览
            print("检测为爬虫，切换为纯浏览模式")
```

> **警告**：修改实例的 `self.tasks` 只影响**当前这个协程**，不影响其他用户。如果修改类属性 `cls.tasks`，会影响全局所有用户，需谨慎使用。

#### C. 基于响应数据的“下一个任务”逻辑
在复杂的业务中，后端可能返回 `next_step` 字段指示客户端下一步操作。

```python
class WorkflowUser(HttpUser):
    @task
    def dynamic_step(self):
        resp = self.client.get("/next_action")
        action = resp.json()["action"]
        
        if action == "verify":
            self.execute(VerifyTaskSet)
        elif action == "complete":
            self.client.post("/finish")
            raise StopUser()  # 流程结束，退出用户
        else:
            # 默认继续当前循环
            return
```

### 3. 实战场景：A/B 测试分流与灰度切换

模拟新老版本的流量切分，在运行时为不同用户分配不同的任务集。

```python
class NewUI(TaskSet):
    @task
    def new_home(self): self.client.get("/v2/home")

class OldUI(TaskSet):
    @task
    def old_home(self): self.client.get("/v1/home")

class ABTestUser(HttpUser):
    def on_start(self):
        # 根据用户 ID 取模决定分组（概率 50%）
        if self.user_id % 2 == 0:
            self.tasks = [NewUI]  # 50% 用户走新 UI
        else:
            self.tasks = [OldUI]  # 50% 用户走旧 UI
        # 注意：这样重写了 tasks，初始定义的 tasks 会被覆盖
```

### 4. 关键差异表：跳过 vs. 选择 vs. 停止

| 操作 | 代码示例 | 当前任务执行 | 后续任务调度 | 用户（协程）状态 |
| :--- | :--- | :--- | :--- | :--- |
| **轻量跳过** | `return` | 立即结束，不报错 | 正常进入下一轮调度 | **存活** |
| **标记失败跳过** | `resp.failure()` + `return` | 计入失败统计 | 正常进入下一轮调度 | **存活** |
| **退出任务集** | `self.interrupt()` | 中断当前 `TaskSet` | 返回父级任务集 | **存活**（除非在顶级） |
| **终止用户** | `raise StopUser()` | 立即中断 | **不调度** | **销毁**（退出） |
| **动态切换模块** | `self.execute(Other)` | 暂停当前，执行 `Other` | `Other` 结束后继续 | **存活** |

### 5. 常见陷阱与性能提示

| 陷阱 | 后果 | 解决方案 |
| :--- | :--- | :--- |
| **在 `@task` 中频繁使用 `self.execute` 嵌套过深** | 调用栈膨胀，难以调试，且可能导致内存泄漏 | 控制嵌套深度不超过 3 层，或使用 `self.interrupt()` 及时返回。 |
| **修改 `self.tasks` 后忘记调整权重字典格式** | 若原 `tasks` 是字典 `{TaskSet: weight}`，直接赋值为列表会导致权重丢失 | 统一使用列表格式（权重均等）或维护字典格式。 |
| **跳过逻辑放在了 `on_start` 中** | `on_start` 无法被调度器跳过，若跳过则导致用户无法启动 | `on_start` 只做必要的初始化，跳过逻辑放在 `@task` 内部。 |
| **动态选择导致某些任务永远不被执行** | 权重分配失效，流量模型失真 | 在 `on_start` 一次性定好 `self.tasks`，运行时尽量少改，或者使用外部数据驱动。 |

---

### 💎 总结

-   **跳过** = **“不买账”**：通过 `return` 或 `self.interrupt()` 优雅放弃，用户活着，继续下一轮。
-   **选择** = **“临时起意”**：通过 `self.execute()` 强行插入新流程，或通过修改 `self.tasks` 改变后续所有调度计划。
-   **核心思想**：让**服务器回包数据**或**用户自身状态**成为控制流的一部分，而不是让脚本像“复读机”一样死板地发送固定比例的请求。
