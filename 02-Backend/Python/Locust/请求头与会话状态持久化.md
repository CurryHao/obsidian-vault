# 请求头与会话状态持久化

在 Locust 中，**请求头（Headers）与会话状态（Session）的持久化管理**，是模拟有状态用户（如已登录用户）的核心能力。这背后不仅是“存一个变量”那么简单，更涉及底层 HTTP 客户端的差异、Token 自动刷新以及协程间的数据隔离。

---

### 1. 底层机制差异：`HttpUser` vs `FastHttpUser`

理解底层客户端的差异，是避免“脚本能跑但状态丢失”的前提。

| 特性 | **`HttpUser` (基于 `requests`)** | **`FastHttpUser` (基于 `geventhttpclient`)** |
| :--- | :--- | :--- |
| **Session 对象** | `requests.Session`，**原生支持** Cookie 持久化与连接复用。 | 轻量级 `HTTPClient`，默认**不自动管理** Cookie。 |
| **Headers 持久化** | 通过 `self.client.headers` 字典持久化，请求时自动合并。 | 通过 `self.client.headers` 字典持久化，请求时自动合并。 |
| **Cookie 处理** | **自动处理**（`Set-Cookie` 自动存入，后续请求自动携带）。 | **需显式开启或手动管理**。需设置 `self.client.cookies` 或手动构造 `Cookie` 头。 |

---

### 2. Headers 持久化：设置、合并与优先级

无论哪种 User 类型，`self.client.headers` 都是一个持久化的类字典对象。

- **设置全局 Headers**：通常在 `on_start` 中执行，一次设置，全生命周期有效。
- **请求级覆盖**：在调用 `get/post` 时传入 `headers` 参数，会**临时覆盖**会话级 Headers 中的同名键，但不会修改会话级 Headers 本身。

```python
from locust import HttpUser, task, between

class AuthUser(HttpUser):
    def on_start(self):
        # 1. 会话级持久化 Headers（作用于该用户的所有请求）
        self.client.headers.update({
            "User-Agent": "Locust/2.x",
            "Accept": "application/json"
        })
        # 假设登录获取 token
        resp = self.client.post("/login", json={"user": "test"})
        token = resp.json()["access_token"]
        # 追加认证头
        self.client.headers.update({"Authorization": f"Bearer {token}"})

    @task
    def profile(self):
        # 此请求自动携带 User-Agent, Accept, Authorization
        self.client.get("/profile")

    @task
    def special_request(self):
        # 请求级覆盖：本次请求将 Accept 临时改为 text/plain
        # 注意：仅本次生效，self.client.headers 中的 Accept 依然是 application/json
        self.client.get("/raw", headers={"Accept": "text/plain"})
```
### 3. Cookie 持久化（Session 状态）

#### A. `HttpUser`：零代码自动管理
`HttpUser` 的 `client` 基于 `requests.Session`。登录接口返回的 `Set-Cookie` 会被自动存储，并在后续请求中自动携带，完全无需手动干预。

```python
class HttpUserExample(HttpUser):
    def on_start(self):
        # 登录后，服务器返回的 Session ID Cookie 自动保存
        self.client.post("/login", json={"username": "test", "password": "123"})
        # 后续 client.get("/dashboard") 会自动携带该 Cookie

    @task
    def dashboard(self):
        self.client.get("/dashboard")  # Cookie 自动附带
```

#### B. `FastHttpUser`：需显式开启或手动管理
`FastHttpUser` 默认**不存储** Cookie。要启用自动 Cookie 管理，需在 `on_start` 中设置 `self.client.cookies`。

```python
from locust import FastHttpUser, task

class FastUserWithCookies(FastHttpUser):
    def on_start(self):
        # 方法一：开启自动 Cookie 管理（推荐，简洁）
        # 注意：需在发起登录请求前设置 cookies 对象
        from geventhttpclient.cookies import CookieJar
        self.client.cookies = CookieJar()
        
        # 登录（此时 Set-Cookie 会自动存入 CookieJar）
        self.client.post("/login", json={"user": "test"})
        
        # 方法二：手动提取并设置（备选，用于特殊场景）
        # resp = self.client.post("/login", json={"user": "test"})
        # session_id = resp.headers.get("Set-Cookie", "").split(";")[0]
        # self.client.headers.update({"Cookie": session_id})

    @task
    def check(self):
        # 自动携带 Cookie
        self.client.get("/profile")
```

### 4. 跨任务集（TaskSet）的状态共享

当使用 `SequentialTaskSet` 或嵌套 `TaskSet` 时，Headers 和 Cookies 存储在 `self.client` 中，天然对所有子任务可见。但如果你需要共享**业务数据**（如订单 ID、用户余额），应挂载在 `self.user`（父级 User 实例）上。

```python
from locust import SequentialTaskSet, task, HttpUser

class CheckoutFlow(SequentialTaskSet):
    @task
    def add_cart(self):
        resp = self.client.post("/cart", json={"id": 1})
        # 将订单号存储在父级 User 实例中，供后续步骤使用
        self.user.order_id = resp.json()["order_id"]

    @task
    def pay(self):
        order_id = self.user.order_id  # 取出共享数据
        self.client.post(f"/pay/{order_id}")
        self.interrupt()
```

### 5. 高级场景：Token 过期自动刷新（401 拦截）

在生产级压测中，Token 可能会在长时间运行时过期。通过 `@events.request` 监听器或 `catch_response` 统一处理 401 状态码，实现“遇过期自动刷新并重试”。

```python
from locust import HttpUser, task, events
import time

class SmartUser(HttpUser):
    token_expire_at = 0

    def refresh_token(self):
        resp = self.client.post("/auth/refresh", json={"refresh": self.refresh_token})
        new_token = resp.json()["access_token"]
        self.client.headers.update({"Authorization": f"Bearer {new_token}"})
        self.token_expire_at = time.time() + 300  # 假设5分钟有效期

    @task
    def critical_api(self):
        # 策略：每次请求前检查是否即将过期（避免无效请求）
        if time.time() > self.token_expire_at - 10:
            self.refresh_token()

        with self.client.get("/api/order", catch_response=True) as resp:
            if resp.status_code == 401:
                # Token 失效（可能因服务端主动吊销），刷新并重试
                self.refresh_token()
                # 手动重试（注意防死循环）
                retry_resp = self.client.get("/api/order")
                if retry_resp.status_code == 200:
                    resp.success()
                else:
                    resp.failure("重试后仍失败")
            elif resp.status_code != 200:
                resp.failure(f"业务错误: {resp.status_code}")
```

### 6. 隔离性：协程间的 Headers/Cookies 完全隔离

在 Locust 中，每个 `User` 实例（Greenlet）拥有**独立的** `self.client` 对象。

- **绝对安全**：用户 A 修改了 `self.client.headers`，不会影响用户 B。
- **适用场景**：这使得每个虚拟用户都能拥有独立的登录态、独立的 Cookie，完美模拟真实多用户并发场景。

### 7. 核心避坑指南（面试/实战高频）

| 陷阱 | 错误表现 | 解决方案 |
| :--- | :--- | :--- |
| **`FastHttpUser` 下 Cookie 丢失** | 登录成功，但后续接口返回 401/重定向到登录页。 | 检查是否设置了 `self.client.cookies = CookieJar()`，或手动管理 `Cookie` 头。 |
| **请求级 Headers 误覆盖全局** | 期望全局携带 `X-Version`，但在某个请求中传了空 `headers={}`，导致全局丢失。 | **优先级规则**：请求级 `headers` 会与全局 `headers` **合并**，而非替换。传递 `{}` 不会清除全局头。若要临时清除，需显式传递 `{"X-Version": None}`（仅部分客户端支持）。 |
| **全局 Headers 包含敏感变量** | Token 硬编码在类属性中，多人协作时泄漏。 | 在 `on_start` 中动态获取，或从环境变量读取（`os.getenv("TOKEN")`）。 |
| **Session 状态在 TaskSet 间丢失** | `TaskSet` A 设置了 `self.user.order_id`，`TaskSet` B 读取为 `None`。 | 检查是否使用了不同的 `User` 实例？确保读写都针对 `self.user`（父级引用）。 |
| **重试风暴（Refresh Token 死循环）** | Token 刷新接口本身返回 401，导致无限重试。 | 在刷新逻辑中增加计数器（如 `retry_count`），超过 3 次直接 `raise StopUser()`。 |

---

### 8. 终极建议：状态管理的“黄金法则”

1.  **认证信息放 Headers**：`Authorization` 或 `Cookie` 通过 `self.client.headers` 持久化。
2.  **业务数据放 `self.user`**：如购物车 ID、当前商品详情，挂载在父级实例上。
3.  **大量固定数据放类变量**：如接口 URL 前缀，不需要每个用户独立时使用类属性。
4.  **优先使用 `HttpUser` 快速验证**：如果服务器支持，先拿 `HttpUser` 验证状态流转逻辑；确认无误后，为了性能再迁移到 `FastHttpUser`（注意调整 Cookie 管理方式）。
