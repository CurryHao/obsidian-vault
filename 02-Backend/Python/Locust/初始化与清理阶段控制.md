# 初始化与清理阶段控制

在 Locust 中，并没有像 `pytest` 或 `unittest` 那样命名为 `setup()` 和 `teardown()` 的全局方法。但是，通过 **`events` 事件系统**，你可以精确地控制压测的**“前置准备”**和**“后置清理”**阶段。

核心区别在于：
- **`on_start` / `on_stop`**：**用户级别**（每个协程执行一次）。
- **`test_start` / `test_stop`**：**测试运行级别**（整个压测生命周期执行一次）。

如果你想要的是“测试开始前准备数据，测试结束后销毁资源”的全局控制，那么 `test_start` 和 `test_stop` 就是标准的 Setup/Teardown 实现。

---

### 1. 基础映射关系

| 传统概念 | Locust 实现 | 执行时机 | 分布式行为 |
| :--- | :--- | :--- | :--- |
| **Setup (前置)** | `@events.test_start` | 点击 `Start` 或 `--headless` 启动时 | **Master 和 Worker 均触发** |
| **Teardown (后置)** | `@events.test_stop` | 点击 `Stop` 或 `-t` 时间耗尽时 | **Master 和 Worker 均触发** |

---

### 2. 分布式下的黄金法则（关键）

在分布式（Master-Worker）模式下，`test_start` 和 `test_stop` **会在所有节点上同时执行**。如果你不加以区分，可能会发生：
- **数据重复插入**：所有 Worker 同时向数据库插入测试数据。
- **端口冲突**：多个 Worker 同时尝试绑定同一个本地端口。
- **文件覆盖**：多个 Worker 同时写入同一个日志文件。

**解决方案：使用 `isinstance` 判断节点角色**

```python
from locust import events
from locust.runners import MasterRunner, WorkerRunner

@events.test_start.add_listener
def on_test_start(environment, **kwargs):
    if isinstance(environment.runner, MasterRunner):
        # ✅ 仅在 Master 执行：创建数据库表、发送通知、刷新 Redis 缓存
        print("[Master] 全局 Setup：初始化 MySQL 表结构")
        # init_database_schema()
    elif isinstance(environment.runner, WorkerRunner):
        # ✅ 仅在 Worker 执行：加载本地缓存、建立连接池
        print("[Worker] 本地 Setup：加载测试数据到内存")
        # load_local_data()

@events.test_stop.add_listener
def on_test_stop(environment, **kwargs):
    if isinstance(environment.runner, MasterRunner):
        # ✅ 仅在 Master 执行：生成最终报告、汇总数据、清理全局资源
        print("[Master] 全局 Teardown：导出最终测试报告")
        # generate_final_report()
    elif isinstance(environment.runner, WorkerRunner):
        # ✅ 仅在 Worker 执行：关闭本地连接、归还资源
        print("[Worker] 本地 Teardown：关闭数据库连接池")
        # close_local_pool()
```
### 3. `test_start` vs `init`：选哪个？

很多初学者分不清 `@events.init` 和 `@events.test_start`，它们有明显的适用边界：

| 维度 | **`@events.init`** | **`@events.test_start`** |
| :--- | :--- | :--- |
| **触发时机** | **进程启动时**（即使只执行 `locust --help` 也会触发） | **实际开始施压时**（点击 Start 按钮） |
| **访问 Runner** | `environment.runner` 可能为 `None` | `environment.runner` **已就绪** |
| **典型用途** | 注册自定义命令行参数 (`--my-arg`) | 动态数据初始化（依赖压测参数的逻辑） |
| **执行次数** | 每个进程启动时 1 次 | 每次测试会话 1 次（Web UI 可多次 Start/Stop） |

**最佳实践**：
- 解析命令行参数 → 放在 `init`。
- 根据解析到的参数加载数据 → 放在 `test_start`。

```python
@events.init_command_line_parser.add_listener
def add_parser(parser):
    parser.add_argument("--env", type=str, default="staging")
    parser.add_argument("--data-version", type=str, default="v2")

@events.test_start.add_listener
def load_data_by_version(environment, **kwargs):
    env = environment.parsed_options.env
    version = environment.parsed_options.data_version
    # 根据参数加载不同的数据集
    load_test_data(env, version)
```

### 4. 完整的生命周期阶段控制（含异常处理）

一个健壮的 Setup/Teardown 需要处理初始化失败的情况，以及防止 Teardown 因为异常而中断。

```python
import gevent
from locust import events
from locust.exception import StopTest

@events.test_start.add_listener
def setup(environment, **kwargs):
    try:
        print("🔧 正在初始化测试环境...")
        # 模拟耗时初始化（如预热数据库连接池）
        gevent.sleep(2)
        
        # 如果初始化失败（如数据库连不上），可以主动终止测试
        # if not check_db_health():
        #     raise StopTest("数据库不可用，终止测试")
            
        print("✅ 测试环境初始化完成")
    except Exception as e:
        print(f"❌ Setup 失败: {e}")
        # 优雅停止，避免无效压测
        environment.runner.quit()

@events.test_stop.add_listener
def teardown(environment, **kwargs):
    try:
        print("🧹 正在清理测试环境...")
        # 关键：清理逻辑务必用 try 包裹，防止因某个清理步骤失败导致整体卡住
        # cleanup_redis_keys()
        # close_database_connections()
        gevent.sleep(1)
        print("✅ 清理完成")
    except Exception as e:
        # 即使清理失败，也不应该阻止进程退出（打印日志即可）
        print(f"⚠️ Teardown 清理异常（忽略）: {e}")
```

### 5. 进阶：利用 `test_start` 动态调节负载曲线

Setup 阶段不仅可以准备数据，还可以动态修改后续的负载行为（例如根据实时时间决定并发数）。

```python
import datetime

@events.test_start.add_listener
def adjust_load_by_time(environment, **kwargs):
    now = datetime.datetime.now().hour
    runner = environment.runner
    
    if 9 <= now <= 11:  # 早高峰
        target_users = 5000
    else:
        target_users = 1000
    
    # 动态调整目标并发（需要 runner 存在且未开始）
    if runner and hasattr(runner, 'target_user_count'):
        runner.target_user_count = target_users
        print(f"根据时间调整并发目标为: {target_users}")
```

### 6. Web UI 多次启停的注意事项

在 Web UI 模式下，你可以多次点击 **Start** 和 **Stop**，每次点击都会触发一次 `test_start` 和 `test_stop`。

**陷阱**：如果你在 `test_start` 中创建了数据库表（`CREATE TABLE IF NOT EXISTS`），重复执行没问题；但如果你在其中 `INSERT` 了测试数据，会导致数据重复插入。

**解决方案**：在 `test_start` 中先执行 `TRUNCATE` 或 `DELETE`，再插入，确保幂等性。

```python
@events.test_start.add_listener
def setup_db(environment, **kwargs):
    if isinstance(environment.runner, MasterRunner):
        # 每次压测开始前，清空上一轮的数据（幂等操作）
        clear_previous_test_data()
        insert_fresh_test_data()
```

### 7. 与用户级生命周期（`on_start`）的协同时序

完整的执行顺序如下（以启动过程为例）：

```text
1. 进程启动 → 触发 init (注册参数)
2. 用户点击 Start → 触发 test_start (全局 Setup)
3. Master 调度并发 → Worker 开始孵化协程
4. 每个协程启动 → 触发 on_start (用户级 Setup)
5. 执行 @task 循环
6. 用户停止/测试结束 → 触发 on_stop (用户级 Teardown)
7. 所有用户停止 → 触发 test_stop (全局 Teardown)
```

### 💎 总结与最佳实践

| 动作 | 推荐位置 | 理由 |
| :--- | :--- | :--- |
| **创建数据库/缓存连接池** | `test_start`（Worker 端） | 每个节点都需要自己的连接，避免跨进程共享。 |
| **初始化全局静态数据**（如 CSV 读入内存） | `test_start`（Worker 端） | 各 Worker 独立副本，避免网络传输锁竞争。 |
| **清空上一轮压测的业务数据** | `test_start`（Master 端） | 只需执行一次，避免重复。 |
| **生成最终 HTML 报告/邮件通知** | `test_stop`（Master 端） | 数据在 Master 端最完整。 |
| **释放数据库连接/关闭文件句柄** | `test_stop`（Worker 端） | 每个节点清理自己的资源。 |
