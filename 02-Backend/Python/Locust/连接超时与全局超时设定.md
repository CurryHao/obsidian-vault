# 连接超时与全局超时设定

在 Locust 中，**超时（Timeout）配置**是保障压测稳定性的最后一道防线。它决定了当目标服务变慢或不可用时，你的压测协程（Greenlet）是“死等”还是“快速失败”。

理解 **连接超时（Connect Timeout）** 与 **读取超时（Read/Network Timeout）** 的区别，并掌握 `HttpUser` 与 `FastHttpUser` 的底层差异，能帮你避免压测机自身因资源耗尽而“雪崩”。

---

### 1. 超时的两个核心阶段

| 阶段 | 官方属性名 | 定义 | 典型场景 |
| :--- | :--- | :--- | :--- |
| **连接超时** | `connection_timeout` | 建立 TCP 三次握手的最大等待时间。 | 目标服务器负载极高，TCP 全连接队列满，无法响应 SYN 包。 |
| **读取超时** | `network_timeout` | 建立连接后，等待服务器返回**响应头或响应体第一个字节**的最大时间。 | 服务器业务逻辑处理慢（如慢 SQL、死锁），或带宽受限导致数据传输缓慢。 |

> **总超时（Total Timeout）**：`HttpUser` 支持将二者合设（元组）；`FastHttpUser` 通常使用单值作为总超时。

---

### 2. 配置层级：全局默认 vs 请求级覆盖

Locust 支持**三级**超时配置，优先级从低到高为：

#### A. 类级全局默认（最常用）
在 `User` 类中直接定义，作用于该用户发出的**所有请求**。

```python
from locust import HttpUser, task

class BaseUser(HttpUser):
    # 连接超时 3 秒，读取超时 10 秒（仅 HttpUser 支持分别设置）
    connection_timeout = 3.0
    network_timeout = 10.0

    @task
    def quick_api(self):
        # 默认使用上述 3s/10s
        self.client.get("/ping")
```
## B. 客户端实例级覆盖（进阶）
在 `on_start` 或 `__init__` 中修改 `self.client` 的属性，影响该用户后续所有请求。对于 `FastHttpUser`，通常会直接修改 `self.client.timeout`（该值覆盖 `network_timeout`）。

```python
class DynamicUser(HttpUser):
    def on_start(self):
        # 根据用户类型动态调整超时
        if self.user_type == "vip":
            self.client.timeout = 5.0  # HttpUser 和 FastHttpUser 均支持
        else:
            self.client.timeout = 2.0
```

#### C. 请求级精准覆盖（最高优先级）
在调用 `get/post` 时传入 `timeout` 参数，**仅本次请求生效**。

```python
@task
def slow_order(self):
    # 下单接口允许更长时间（覆盖全局 10s，设为 30s）
    self.client.post("/order", json={...}, timeout=30)

@task
def health_check(self):
    # 健康检查接口苛刻（覆盖全局，设为 2s）
    self.client.get("/health", timeout=2)
```

### 3. `HttpUser` vs `FastHttpUser` 的超时机制（核心差异）

这是最容易被忽视的踩坑点：

| 特性 | **`HttpUser` (基于 requests)** | **`FastHttpUser` (基于 geventhttpclient)** |
| :--- | :--- | :--- |
| **是否支持分离超时** | ✅ **支持**。`timeout=(connect_sec, read_sec)` | ❌ **不支持元组**。只接受单个 `float`，代表**总请求超时**（连接+读取的总和）。 |
| **类属性映射** | `connection_timeout` / `network_timeout` | **仅 `network_timeout`** 生效（用作总超时）。`connection_timeout` 被忽略或需通过底层 client 设置。 |
| **默认值** | 若未设置，默认 `None`（无限等待，**风险极高**） | 默认 `None`（无限等待，风险极高） |
| **超时异常类型** | `requests.exceptions.ConnectTimeout` / `ReadTimeout` | `geventhttpclient.exceptions.Timeout`（统一异常） |

**实战指引**：
```python
# ✅ HttpUser 推荐写法（精准控制）
class MyHttpUser(HttpUser):
    connection_timeout = 2.0  # 连接快超
    network_timeout = 15.0    # 处理慢接口容忍度高

    @task
    def api(self):
        # 特殊接口：连接3秒，读取30秒（仅 HttpUser 有效）
        self.client.post("/large_upload", timeout=(3.0, 30.0))

# ✅ FastHttpUser 推荐写法（简洁总时长）
class MyFastUser(FastHttpUser):
    network_timeout = 10.0  # 整个请求（连接+读取）最多10秒

    @task
    def api(self):
        # 覆盖总时长为 5 秒
        self.client.get("/fast", timeout=5)
```

### 4. 连接超时与“全局最大并发”的隐藏关联

- **陷阱**：若 `timeout` 设置过长（如 120s）且目标服务出现故障，所有协程都会卡在 `read()` 上等待超时，**导致有效并发数（活跃 Greenlet）骤降**，即使 `-u` 设了 1000，实际能执行任务的可能只有几十个。
- **策略**：**快速失败（Fail Fast）**。对于非核心接口，将超时设为 3~5 秒，配合 `catch_response` 捕获超时异常并记录失败，然后让该用户继续执行下一个任务（或直接 `raise StopUser()` 释放资源）。

---

### 5. 实战：主动捕获超时并优雅降级

结合 `catch_response`，你可以精准处理超时情况，避免协程卡死：

```python
from locust import HttpUser, task
from requests.exceptions import Timeout  # HttpUser 的异常
from geventhttpclient.exceptions import Timeout as GTimeout  # FastHttpUser 的异常

class ResilientUser(HttpUser):
    connection_timeout = 2
    network_timeout = 5

    @task
    def unstable_api(self):
        try:
            with self.client.get("/unstable", catch_response=True, timeout=3) as resp:
                if resp.status_code == 200:
                    resp.success()
                else:
                    resp.failure(f"HTTP {resp.status_code}")
        except Timeout as e:
            # 捕获超时，标记失败但不阻塞用户
            # 注意：在 catch_response 块外捕获异常
            print(f"请求超时，跳过该任务: {e}")
            # 此处无法直接调用 resp.failure，需通过 events 手动记录或忽略
```

**更好的做法**：直接在 `with` 块内处理超时（但 `catch_response` 默认**不会**捕获网络层异常，需结合 `try-except`）：

```python
@task
def safe_request(self):
    try:
        with self.client.get("/api", catch_response=True, timeout=5) as resp:
            # 正常业务校验
            resp.success() if resp.status_code == 200 else resp.failure("业务错")
    except Exception as e:
        # 处理连接超时、DNS错误等底层异常
        # 手动上报失败统计（推荐）
        self.environment.events.request.fire(
            request_type="GET",
            name="/api",
            response_time=0,
            response_length=0,
            exception=e,
            context={},
        )
        # 若连续超时，退出用户避免僵尸
        if getattr(self, '_timeout_count', 0) > 3:
            raise StopUser()
        self._timeout_count = getattr(self, '_timeout_count', 0) + 1
```

### 6. 全局强制兜底：`--max-rps` 与资源限制

虽然 `timeout` 控制单次请求，但 **`--max-rps`** 可以控制全局最大吞吐量，避免在超时重试时瞬间压垮压测机本身。

- 配合使用：`timeout` 防止协程卡死，`--max-rps` 防止机器网络缓冲区溢出。

---

### 7. 快速决策速查表

| 场景描述 | 推荐超时设置 | 理由 |
| :--- | :--- | :--- |
| **健康检查（/health）** | 1~2 秒 | 必须极快响应，超时即代表服务不可用。 |
| **普通查询（GET）** | `connection_timeout=3`，`network_timeout=5` | 平衡用户体验与快速失败。 |
| **下单/支付（POST）** | `timeout=30` 或 60 秒 | 涉及事务、库存扣减，允许较长处理时间。 |
| **大文件下载/导出** | `timeout=120`（或 `stream=True`） | 若使用 `HttpUser`，建议 `stream=True` 配合读取超时。 |
| **压测机性能瓶颈** | 缩短超时（如 3s） | 避免协程堆积在等待上，消耗内存。 |

---

### 💎 总结

1.  **务必设置全局默认超时**：无论是 `connection_timeout`/`network_timeout`（HttpUser）还是 `network_timeout`（FastHttpUser），**绝不要留 `None`**，否则生产故障会导致压测机资源耗尽。
2.  **区分客户端差异**：若从 `HttpUser` 迁移到 `FastHttpUser`，记得把 `timeout=(c, r)` 拆成单一 `float`（取较大值），否则会抛 `TypeError`。
3.  **长超时配合短重试**：若业务必须长超时（如 60s），务必在代码中实现**超时计数器**，连续超时 3 次后主动 `StopUser`，防止资源被“僵尸协程”耗尽。
