# Web仪表盘核心指标解读

在 Locust 的 Web 仪表盘中，**RPS（吞吐量）**、**响应时间**和**并发用户数**构成了评估系统性能的“铁三角”。这三者相互关联，共同描绘出目标系统在负载下的行为画像。能够“读懂”它们之间的联动关系，是定位性能瓶颈的关键。

---

### 1. RPS（Requests Per Second）：系统吞吐的“速度表”

RPS 表示系统每秒钟能处理多少请求，是衡量系统处理能力最直接的指标。

- **监控价值**：通过观察 RPS 的变化，可以判断系统是否达到了吞吐上限。如果增加并发用户数，RPS 却不再增长甚至下降，说明系统可能已达到性能瓶颈（如数据库连接池满、CPU 100%）。
- **解读要诀**：
    - **理想情况**：RPS 随并发用户数线性增长。
    - **危险信号**：RPS 增长放缓或下降，可能意味着系统资源饱和或出现锁竞争。
    - **联动分析**：RPS 下降的同时，如果响应时间急剧上升，通常是系统过载的典型表现。

---

### 2. 响应时间：用户体验的“温度计”

响应时间反映了用户等待请求返回的速度，直接影响最终用户的体验。在仪表盘中，通常重点关注百分位数（如 **P95**、**P99**），而非平均值。

- **平均值（Avg）**：容易被少数极端慢请求“平均”掉，掩盖大部分慢请求，参考价值有限。
- **中位数（Median）**：表示 50% 的请求在多少时间内完成，反映了大多数用户的体验。
- **P95 / P99**：表示 95% 或 99% 的请求在多少时间内完成。**建议重点关注 P95**，因为它能有效排除极值干扰，反映头部用户的体验。P99 则用于排查极端长尾延迟问题。
- **解读要诀**：
    - **健康状态**：P95 响应时间保持平稳，且低于设定的 SLA 阈值。
    - **危险信号**：响应时间曲线出现毛刺或持续上升，通常意味着系统处理能力不足或存在资源争用。当响应时间曲线与 RPS 曲线出现“剪刀差”（即 RPS 开始下降而响应时间继续飙升）时，是系统即将崩溃的强烈预警信号。

---

### 3. 并发用户数（Current Users）：压力的“油门踏板”

并发用户数（`Total Users`）表示当前 Locust 实际模拟的在线用户数量。它不同于用户数，在 Locust 中，它代表的是当前活跃的协程数量。

- **注意点**：在 Web 仪表盘左侧，你会看到 **`Total Users`** 和 **`Users`** 两个数值。
    - **`Total Users`**：是 Master 节点记录的实际活跃用户总数，它会在设定的目标值（如 `1000`）附近波动。如果实际用户数长期低于目标值，说明 Worker 节点可能正在高频退出，或者 CPU 资源不足以支撑目标并发。
    - **`Users`**：通常指 Worker 节点的本地统计，分布式下需关注 `Total Users`。
- **解读要诀**：
    - **瓶颈判别**：如果 `Total Users` 已达到目标值，但 RPS 无法继续提升，那么目标系统本身处理能力可能不足。
    - **压测机负载**：如果 `Total Users` 频繁无法达到目标值，或出现异常抖动，则可能是压测机自身的资源（CPU/内存）已达上限，或者 `wait_time` 设置过长。

---

### 4. 关联模型：铁三角的联动关系（动态分析）

这三个指标并非孤立，理解它们的联动关系是分析性能问题的核心：

1.  **正常状态**：增加并发用户数，RPS 同步增长，响应时间保持稳定。
2.  **系统瓶颈出现**：继续增加并发用户数，RPS 增长趋缓或停滞，响应时间开始上升。此时系统已接近性能拐点（Saturation Point）。
3.  **系统过载**：进一步加压，RPS 开始下降，响应时间急剧飙升，并发用户数也可能出现波动（因超时导致用户退出）。此时的用户体验已严重受损。

### 🔍 实战误区警示

在解读仪表盘时，要警惕以下“健康假象”，避免被表面的“绿色”指标误导：

| 现象描述 | 背后可能隐藏的问题 |
| :--- | :--- |
| **RPS 高，但响应时间极低** | 可能是压测脚本未正确加 `name` 参数，导致所有请求被聚合，指标无区分度。 |
| **平均响应时间正常，但 P99 奇高** | 系统存在慢查询，只有少数用户受影响，但可能涉及关键路径。 |
| **失败率为 0，但业务失败率极高** | 未使用 `catch_response` 进行业务断言，HTTP 200 掩盖了业务码错误。 |
| **并发用户数稳定，但 RPS 开始下降** | 接口响应变慢，导致每个用户单位时间内能发起的请求数减少。 |
| **添加大量 Worker 后 RPS 仍不增长** | 瓶颈可能在 Master（统计聚合）或目标系统（连接池/网络带宽）。 |

### 💎 与分布式场景的结合

在分布式压测中，Web 仪表盘（运行在 Master 上）显示的是**所有 Worker 聚合后的全局数据**。此时，若发现 RPS 或响应时间异常，需要同时检查：

- **是否有个别 Worker 掉线或繁忙不均**（可通过 `--stats-history` 或自定义监控查看）。
- **Master 是否成为瓶颈**（Master CPU 使用率是否达到 100%）。

因此，将 Locust Web 仪表盘与 **Grafana/Prometheus** 监控体系联动，是生产级压测的常见实践。如果下一步你想了解如何通过 `locust.conf` 配置统计采样率，或深入 `--csv` 导出的数据字段含义，可以随时提出。
