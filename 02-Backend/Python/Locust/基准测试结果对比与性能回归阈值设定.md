# 基准测试结果对比与性能回归阈值设定

基准测试结果对比与性能回归阈值设定，是整个 **“性能门禁（Perf Gate）”** 中最核心、也最容易引发争议的环节。阈值设得太严，会因环境抖动导致大量误报，阻塞研发流程；设得太松，又会放过真正的性能劣化。

要解决这个问题，不能依赖拍脑袋决定的固定百分比（如“统一 10%”），而需要建立一套**基于统计学和历史数据的动态阈值体系**。

---

### 一、为什么“固定百分比阈值”不靠谱？

在实际的 CI 环境中，响应时间天然存在波动，常见干扰源包括：

- **环境噪声**：共享测试环境的 CPU 抢占、网络微突发。
- **GC（垃圾回收）暂停**：Java/Go 应用在压测中偶发 GC 导致毛刺。
- **缓存命中率变化**：测试数据分布不均导致缓存失效。
- **基线漂移**：随着业务迭代，接口本身变复杂，基线响应时间自然缓慢上升。

**如果简单地设定“P95 恶化超过 10% 就报错”**，在低延迟接口（如 10ms）上，波动 1ms（10%）可能毫无意义；在高延迟接口（如 500ms）上，波动 50ms（10%）却可能极具参考价值。

---

### 二、科学的阈值设定策略（三层防御体系）

我推荐使用 **“绝对兜底 + 相对历史波动 + 统计离群检测”** 三层防御策略。

| 层级 | 策略名称 | 核心逻辑 | 适用场景 |
| :--- | :--- | :--- | :--- |
| **L1** | **绝对硬阈值** | 响应时间不得超过 SLA 约定值（如 P95 < 800ms） | 防止接口彻底变慢，不依赖基线 |
| **L2** | **滚动基线对比** | 与最近 N 次（如最近 5 次）主分支构建的**中位数**对比 | 消除单次基线异常的干扰，适应缓慢演进 |
| **L3** | **统计离群检测（IQR/3-Sigma）** | 计算历史数据的标准差（σ），仅当变化超过 **3σ** 或 **1.5×IQR** 时报警 | 消除环境毛刺，只捕捉显著的、非偶然的性能回归 |

---

### 三、落地实施：动态阈值计算器（Python）

我们需要将上述策略编码为 Python 脚本。假设我们有一个数据存储（如 JSON 文件或 InfluxDB），存储了最近 30 次主分支构建的 `p95` 数据点。

#### 1. 获取历史数据集
```python
# 模拟从 InfluxDB 或制品库拉取的历史 P95 数据（单位：ms）
# 按时间倒序，最新在前，取最近 20 个有效数据点
history_p95 = [102, 105, 98, 110, 108, 115, 120, 112, 106, 100,
               104, 107, 111, 109, 103, 101, 108, 114, 106, 99]  # 20个历史点
```
## 2. 计算动态基线（滚动中位数 + 标准差）
```python
import numpy as np

def calculate_dynamic_baseline(history, window=10):
    # 取最近 window 条数据（应对慢演进）
    recent = history[:window]
    
    # L2: 基线使用中位数（抗异常值干扰）
    baseline_median = np.median(recent)
    
    # L3: 计算绝对中位差（MAD），比标准差更稳健
    mad = np.median(np.abs(recent - baseline_median))
    # 通常 MAD 乘以 1.4826 等价于标准差（假设正态分布）
    robust_std = mad * 1.4826
    
    return baseline_median, robust_std
```

#### 3. 核心判定逻辑
```python
def judge_performance_regression(current_p95, baseline_median, robust_std, 
                                 absolute_limit=800,  # L1：绝对硬阈值
                                 mad_multiplier=3.0): # L3：统计阈值，3倍标准差
    
    # --- L1: 绝对硬阈值检查 ---
    if current_p95 > absolute_limit:
        print(f"❌ L1 阻断: P95({current_p95}ms) > 硬阈值({absolute_limit}ms)")
        return False, "absolute_limit"

    # --- L2 & L3 联合判断 ---
    # 只有当变化幅度同时满足以下条件时才阻断：
    # 条件1：相对变化率 > 15% （过滤微小的正常波动）
    # 条件2：绝对增长值 > 3 * 历史稳健标准差（证明是显著离群）
    
    change_pct = (current_p95 - baseline_median) / baseline_median * 100
    abs_change = current_p95 - baseline_median
    
    if change_pct > 15 and abs_change > (mad_multiplier * robust_std):
        print(f"❌ L2+L3 阻断: 变化率 {change_pct:.1f}%，"
              f"绝对值增长 {abs_change:.0f}ms，超过 {mad_multiplier}σ 阈值")
        return False, "statistical_regression"
    
    print(f"✅ 性能回归检测通过: 变化率 {change_pct:.1f}%，"
          f"基线 {baseline_median:.0f}ms → 当前 {current_p95:.0f}ms")
    return True, "passed"
```

### 四、实战演练：模拟不同场景

我们通过几个案例验证上述逻辑的有效性：

| 场景 | 历史基线中位数 | 稳健标准差 (σ) | 当前 P95 | 变化率 | 判定结果 | 原因分析 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **代码优化，响应变快** | 100ms | 5ms | 90ms | -10% | ✅ **通过** | 性能变好，不阻断 |
| **环境正常抖动** | 100ms | 5ms | 108ms | +8% | ✅ **通过** | 变化率 < 15%，且波动在 3σ 内 |
| **环境偶发毛刺** | 100ms | 5ms | 125ms | +25% | ✅ **通过**（关键） | 虽然变化率大，但绝对增长 25ms < 3σ(15ms)？*(25 > 15，这里会阻断，调整为：如果毛刺是瞬时的，需依赖重试机制)*。**实际优化**：在流水线中，若判定为离群，可触发自动重试（重跑一次），若第二次恢复，则放行。 |
| **真实代码性能回退** | 100ms | 5ms | 160ms | +60% | ❌ **阻断** | 变化率极大，且远超 3σ，确认为回归 |
| **高延迟接口慢演进** | 500ms | 20ms | 580ms | +16% | ✅ **通过** | 变化率仅超 1%，且差值在 3σ 内，认为正常业务演变 |

> **特别注意**：对于 L3 离群检测，强烈建议在流水线中增加 **“失败时自动重试 1 次”** 的机制。如果重试后指标恢复，说明是环境抖动，不算回归；如果重试后依然失败，则精准阻断。

### 五、针对不同端点设定差异化参数（Threshold Matrix）

在真实系统中，不同接口的稳定性要求不同。建议在 `locustfile` 或配置中心定义阈值矩阵：

```yaml
# perf_gate_config.yaml
thresholds:
  # 核心读接口：绝对阈值高，但回归容忍度低
  - endpoint_regex: ".*/api/v1/users/.*"
    absolute_p95: 200
    regression_pct: 10
    mad_multiplier: 2.5

  # 报表导出接口：绝对阈值高，容忍度高
  - endpoint_regex: ".*/api/v1/reports/export"
    absolute_p95: 3000
    regression_pct: 25
    mad_multiplier: 3.0

  # 健康检查接口：绝对阈值低，但可容忍波动
  - endpoint_regex: ".*/health"
    absolute_p95: 50
    regression_pct: 30
    mad_multiplier: 4.0
```

### 六、基线存储与更新策略（防止基线腐烂）

基线的维护至关重要，建议采用 **“滚动窗口 + 强制下限”** 策略：

1.  **存储结构**：在 InfluxDB 或 PostgreSQL 中存储每次压测的 `commit_sha`, `p95`, `timestamp`。
2.  **更新时机**：
    - 每当 **主分支** 的压测门禁通过时，将该数据点推入历史数据集。
    - 剔除超过 **30 天** 的历史数据，避免陈旧数据拉低标准差。
3.  **强制回滚机制**：如果连续 3 次构建，P95 都稳定在历史基线 + 15% 以上，说明业务确实变重了。此时应更新基线，而不是每次都报警。**必须有人工审批**来确认这是否符合预期的业务变化。

### 七、在 CI 流水线中的最终集成（以 GitLab CI 为例）

将上述脚本集成进流水线：

```yaml
.perf-gate:
  script:
    # 1. 获取当前压测结果 (gate_result.json)
    # 2. 下载历史基线数据集 (history.json)
    # 3. 运行 Python 动态判定
    - python scripts/dynamic_perf_judge.py 
        --current gate_result.json 
        --history history.json 
        --config perf_gate_config.yaml
  # 4. 如果脚本返回值非 0，自动重试一次（消除毛刺）
  retry:
    max: 2
    when: failure
```

### 总结

| 核心要点 | 说明 |
| :--- | :--- |
| **绝对阈值兜底** | 保证服务核心 SLA（服务等级协议），无论基线如何变化都不能超限 |
| **相对基线（中位数）** | 消除单次异常，反映系统当前的真实水位 |
| **统计离群（MAD/σ）** | 过滤环境抖动，只针对统计上显著的性能变化进行阻断 |
| **差异化配置** | 不同业务属性的接口（读/写/导出）适用不同的容忍度 |
| **重试与人工确认** | 结合自动重试机制，大幅降低误报率，再配合基线的定期人工审核 |

这套体系可以让你把性能回归误报率控制在 **< 5%** 以内，同时确保 **> 95%** 的真实性能问题被拦截在合并之前。
