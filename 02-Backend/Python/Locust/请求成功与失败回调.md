# 请求成功与失败回调

在 Locust 中，`request_success` 与 `request_failure`（或统一的 `events.request`）是**请求级别**的回调事件，它们在**每一次请求完成时**被触发。这使得它们成为实现**实时监控、自定义日志、失败分类、外部数据推送**以及**自适应负载控制**的理想钩子。

---

### 1. 现代推荐方式：统一的 `events.request`

自 Locust 1.x 起，官方推荐使用统一的 `events.request` 事件，它通过 `exception` 参数区分成功与失败，代码更简洁。

```python
from locust import events

@events.request.add_listener
def on_request(request_type, name, response_time, response_length, response,
               exception, context, **kwargs):
    """
    每次请求完成后触发。
    若 exception 为 None，则请求成功；否则表示失败。
    """
    if exception is None:
        # 请求成功
        print(f"[OK] {request_type} {name} - {response_time:.2f}ms")
    else:
        # 请求失败
        print(f"[FAIL] {request_type} {name} - {exception}")
```
**关键参数**：
- `request_type`：如 `"GET"`、`"POST"`、`"WEBSOCKET"`。
- `name`：统计名称（你设置的 `name` 参数或自动提取的 URL）。
- `response_time`：响应时间（毫秒）。
- `response_length`：响应体长度（字节）。
- `response`：响应对象（仅当成功且可获取时）。
- `exception`：失败时为异常对象，成功时为 `None`。
- `context`：通过 `self.client.get(..., context={"key": "value"})` 传递的自定义数据。

---

### 2. 旧版独立事件（仍可用）

在早期 Locust 中，有独立的 `request_success` 和 `request_failure` 事件。当前版本仍然支持，但官方文档更推荐使用统一的 `events.request`。

```python
@events.request_success.add_listener
def on_success(request_type, name, response_time, response_length, **kwargs):
    print(f"成功: {name} - {response_time}ms")

@events.request_failure.add_listener
def on_failure(request_type, name, response_time, response_length, exception, **kwargs):
    print(f"失败: {name} - {exception}")
```

### 3. 典型实战场景

#### A. 实时失败分类与告警
根据异常类型或 HTTP 状态码进行分级告警。

```python
from locust import events
import requests.exceptions

@events.request.add_listener
def classify_failure(exception, name, **kwargs):
    if exception is None:
        return
    if isinstance(exception, requests.exceptions.Timeout):
        alert_type = "TIMEOUT"
    elif isinstance(exception, requests.exceptions.ConnectionError):
        alert_type = "CONNECTION_REFUSED"
    elif hasattr(exception, 'response') and exception.response is not None:
        alert_type = f"HTTP_{exception.response.status_code}"
    else:
        alert_type = "OTHER"
    
    # 仅对严重错误发送告警（例如超时或拒绝连接）
    if alert_type in ("TIMEOUT", "CONNECTION_REFUSED", "HTTP_500", "HTTP_503"):
        send_alert(name, alert_type, str(exception))
```

#### B. 记录业务错误码（与 `catch_response` 联动）
当你在 `catch_response` 中调用 `resp.failure("业务错误")` 时，`exception` 参数会收到一个包含你传入消息的异常对象。

```python
@task
def my_api(self):
    with self.client.get("/api", catch_response=True, context={"user_id": self.user_id}) as resp:
        data = resp.json()
        if data.get("code") != 0:
            resp.failure(f"业务错误: {data.get('msg')}")
        else:
            resp.success()

@events.request.add_listener
def on_request(exception, context, **kwargs):
    user_id = context.get("user_id")
    if exception:
        # exception 是 resp.failure() 中传入的字符串（通过 AssertionError 包装）
        print(f"用户 {user_id} 业务失败: {exception}")
```

#### C. 持久化到外部时序数据库（InfluxDB / Prometheus）
在高并发下，**务必采用批量或采样方式**，避免影响性能。

```python
from influxdb import InfluxDBClient
import gevent

# 使用队列异步写入
influx_client = InfluxDBClient(host='localhost', port=8086, database='locust')
batch = []
BATCH_SIZE = 50

@events.request.add_listener
def push_to_influx(request_type, name, response_time, exception, **kwargs):
    point = {
        "measurement": "locust_requests",
        "tags": {"type": request_type, "name": name},
        "fields": {
            "response_time": response_time,
            "success": 0 if exception else 1,
        }
    }
    batch.append(point)
    if len(batch) >= BATCH_SIZE:
        # 异步发送，避免阻塞
        gevent.spawn(influx_client.write_points, batch)
        batch.clear()
```

#### D. 记录慢请求到独立日志
筛选响应时间超过阈值的请求。

```python
@events.request.add_listener
def on_request(response_time, name, exception, **kwargs):
    if exception is None and response_time > 5000:  # 5秒
        with open("slow_requests.log", "a") as f:
            f.write(f"{time.ctime()}, {name}, {response_time}ms\n")
```

#### E. 自适应负载控制（高风险，谨慎使用）
根据失败率动态减少并发用户数，但需注意与统计冲突。

```python
failure_counter = 0
total_counter = 0

@events.request.add_listener
def on_request(exception, environment, **kwargs):
    global failure_counter, total_counter
    total_counter += 1
    if exception:
        failure_counter += 1
    if total_counter % 100 == 0:
        if failure_counter / total_counter > 0.1:  # 10% 失败率
            runner = environment.runner
            if runner and runner.user_count > 20:
                # 通过停止部分用户来降低并发（非官方API，需谨慎）
                # 更安全的方式是发出告警或停止测试
                print("失败率过高，建议停止测试")
```

### 4. 分布式环境下的行为

- `events.request` 在**每个 Worker 节点本地触发**，不会自动发送到 Master。
- 如果你想在 Master 上汇总所有请求的额外指标（如自定义失败分类），有两种方式：
  1. 在 Worker 上通过队列将数据发回 Master（需自定义消息）。
  2. 仅在 Master 上使用 `events.request`（但 Master 不发送请求，所以不会触发）。因此，通常这种监听器在 Worker 上执行，用于本地日志或外部推送。

---

### 5. 性能注意事项

| 操作 | 性能影响 | 优化建议 |
| :--- | :--- | :--- |
| **打印语句（print）** | 极高，会拖慢并发 | 仅用于调试，生产环境使用 `logging` 并设置合适级别。 |
| **同步文件写入** | 高，磁盘 I/O 成为瓶颈 | 使用异步队列（如 `queue.Queue` + 后台线程）批量写入。 |
| **网络请求（如推送 InfluxDB）** | 非常高，每个请求都有网络开销 | 使用批量缓冲 + 异步发送，或采样（如 1/100 采样）。 |
| **复杂计算（如正则、JSON解析）** | 中高，消耗 CPU | 尽量简化，或将计算移至 `catch_response` 块中（但会占用请求时间）。 |
| **访问 `environment.runner.stats`** | 中，但频繁读取可能导致锁竞争 | 仅在必要时读取（如每 100 个请求统计一次）。 |

### 6. 与 `test_start`/`test_stop` 的协作

- **`test_start`**：注册一个后台协程，用于定时从队列中消费数据并上报。
- **`events.request`**：将数据放入队列。
- **`test_stop`**：将剩余队列数据刷出。

示例架构：

```python
import gevent
from collections import deque

data_queue = deque()

@events.test_start.add_listener
def start_consumer(environment, **kwargs):
    def consumer():
        while True:
            gevent.sleep(1)
            if data_queue:
                # 批量发送
                send_batch(list(data_queue))
                data_queue.clear()
    gevent.spawn(consumer)

@events.request.add_listener
def on_request(response_time, name, exception, **kwargs):
    data_queue.append({"name": name, "rt": response_time, "fail": bool(exception)})

@events.test_stop.add_listener
def flush_on_stop(**kwargs):
    if data_queue:
        send_batch(list(data_queue))
```

### 7. 常见陷阱与避坑指南

| 陷阱 | 后果 | 解决方案 |
| :--- | :--- | :--- |
| **在回调中未区分 Master/Worker** | 若在 Master 上也注册了，由于 Master 不发送请求，不会触发，反而浪费性能。 | 通常无需判断，因为 Master 不发送请求，回调不会执行。 |
| **阻塞回调导致整体吞吐下降** | 每个请求都要等待回调完成，吞吐量暴跌。 | 所有 I/O 操作改为异步或批量，回调仅做轻量计算。 |
| **直接使用 `response.text` 或 `response.json()`** | 可能触发解码或解析，增加 CPU 开销。 | 在 `catch_response` 中已经解析过，此处可避免再次解析。若必须，可缓存结果到 `response` 对象。 |
| **记录所有请求到日志文件** | 日志文件迅速膨胀，磁盘写满。 | 只记录失败或慢请求，且使用循环日志。 |
| **依赖 `exception` 的消息字符串做逻辑判断** | 异常消息可能变化，不利于维护。 | 优先使用异常类型（`isinstance`）或自定义异常类。 |

### 💎 总结

- **`events.request`** 是请求级别的实时回调，适合**监控、日志、外部集成**。
- 通过 `exception` 参数区分成功与失败，通过 `context` 传递业务上下文。
- **性能优先**：回调必须轻量，大开销操作移至后台协程或批量处理。
- 与 `test_start`/`test_stop` 配合，可实现完整的数据采集与报告闭环。

如果你需要**将请求数据按自定义维度（如用户角色、地域）聚合**，或者想**在回调中实现动态调节每个用户的 `wait_time`**，可以告诉我，我们继续深入。
